## 2. 가용성 개념

### 2.1 가용성이란

가용성은 **워크로드를 사용할 수 있는 시간의 비율**입니다. "사용할 수 있다"는 것은
필요할 때 합의된 기능을 성공적으로 수행한다는 뜻입니다.

```text
가용성 = 사용 가능 시간 / 전체 시간
```

한 달, 1년, 또는 3년 추적 기간으로 계산합니다. **엄격하게 해석하면 계획된 중단도
가용성을 깎습니다.** 계획된 유지 관리를 전체 시간에서 빼는 고객도 있지만
🆕 AWS 는 이를 권장하지 않습니다. 사용자는 그 시간에도 서비스를 쓰고 싶어 하기 때문입니다.

🆕 시간 대신 **요청 수**로 세는 방법도 있습니다.

```text
가용성 = 성공 응답 수 / 유효 요청 수
```

보통 1분 또는 5분 단위로 측정하고, 그 평균으로 월간 가동 시간 비율을 냅니다. 어떤 구간에
요청이 없으면 그 구간은 100% 로 계산합니다.

### 2.2 "9가 몇 개"의 실제 의미

| 가용성 | 연간 최대 비가용성 | 일반적인 애플리케이션 유형 |
|---|---|---|
| 99% | 3일 15시간 | 배치 처리, 데이터 추출·전송·로드 작업 |
| 99.9% | 8시간 45분 | 지식 관리, 프로젝트 추적 같은 **내부 도구** |
| 99.95% | 4시간 22분 | 온라인 상거래, POS |
| 99.99% | 52분 | **동영상 전송**, 브로드캐스트 워크로드 |
| 99.999% | 5분 | ATM 트랜잭션, **통신 워크로드** |

가용성 목표는 **비즈니스 목표와 일치해야** 합니다. 가동 중단 시간을 0으로 만들 수는
없지만 몇 초 또는 몇 분으로 줄이는 것이 목표입니다.

> — 출처: [Availability (Reliability Pillar)](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)

### 2.3 가용성 계산의 두 가지 방향 🆕

이 부분은 교재에 없지만 설계 결정을 이해하는 데 꼭 필요합니다.

**하드 종속성은 가용성을 곱해서 깎습니다.** 종속 시스템의 중단이 곧 내 시스템의
중단으로 이어지는 관계입니다.

```text
99.99% 시스템이 각각 99.99% 인 독립 시스템 두 개에 하드 종속

0.9999 × 0.9999 × 0.9999 = 0.9997  →  99.97%
```

**독립 중복 구성 요소는 가용성을 올립니다.** 서로 다른 AZ 의 중복 리소스가 그 예입니다.

```text
99.9% 구성 요소 두 개를 독립 중복으로

100% − (0.1% × 0.1%) = 99.9999%
```

빠른 계산법: 가용성이 모두 9로만 되어 있으면 **9의 개수를 더하면** 됩니다.
9가 3개인 구성 요소 두 개를 중복하면 9가 6개가 됩니다.

**설계에 주는 함의는 분명합니다.** 종속성을 줄이고 중복성을 늘려야 합니다. 그리고
내 워크로드의 가용성을 계산할 때 **의존하는 모든 것의 가용성 목표를 알아야** 합니다.

> — 출처: [Availability (Reliability Pillar)](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/availability.html)

### 2.4 높은 가용성의 비용 🆕

가용성을 높이면 비용이 올라갑니다. 인프라 비용만이 아닙니다.

- 모든 종류의 실패 시나리오에 대한 **철저한 테스트와 검증**이 필요합니다
- 모든 실패로부터의 복구를 **자동화**해야 합니다
- 용량 추가·제거, 배포와 롤백, 데이터 마이그레이션까지 **같은 목표 수준으로** 수행해야
  합니다
- 매우 높은 수준에서는 배포를 천천히 해야 하므로 **혁신 속도가 떨어집니다**

그래서 **설계에 들어가기 전에 진짜 필요한 가용성 수준을 정하는 것**이 순서입니다.

## 3. 장애 조치 계획

### 3.1 세 가지 수준

| 수준 | 대비 방법 |
|---|---|
| **인스턴스 장애 조치** | Auto Scaling 그룹 + 상태 확인 (모듈 2) |
| **가용 영역 장애 조치** | 다중 AZ 서브넷 + ELB (모듈 1\~2) |
| **리전 장애 조치** | 다중 리전 배포 + **Route 53 라우팅 정책** (이 모듈) |

### 3.2 리전 격리

AWS 는 **엄격한 리전 격리 정책**을 유지합니다. 한 리전의 대규모 이벤트가 다른 리전에
영향을 주지 않도록 설계되어 있습니다.

고객도 같은 접근을 하는 것이 권장됩니다. **각 리전은 다른 리전에 영향을 주지 않고
오프라인으로 전환할 수 있어야** 합니다.

빠른 배포에는 **활성/활성 리전** 구성이 권장됩니다. 배포 때문에 한 리전의 애플리케이션이
오작동하면 이렇게 대응합니다.

1. Route 53 의 활성 레코드 세트에서 **해당 리전을 제거**합니다
2. 근본 원인을 확인합니다
3. 변경 사항을 롤백합니다
4. 해당 리전을 **다시 활성화**합니다

### 3.3 다중 리전을 뒷받침하는 것

리전을 늘리려면 인프라를 **반복 가능하게** 만들어야 합니다. 교재는 코드형 인프라(IaC)를
짚습니다.

| 도구 | 역할 |
|---|---|
| AWS CloudFormation | JSON/YAML 템플릿으로 전체 스택을 정의합니다. **의사 파라미터**로 배포된 계정·리전을 식별하고, 조건 논리로 DR 리전에는 축소판을 배포할 수 있습니다 |
| EC2 Image Builder | 필요한 AMI 를 만드는 파이프라인. AMI 를 기본·백업 리전에 복사해 둡니다 |
| AWS CLI / SDK | 스크립트로 리소스를 프로비저닝합니다 |

IaC 의 이점은 네 가지입니다.

| 이점 | 내용 |
|---|---|
| 빠른 속도와 높은 안전성 | 프로그래밍 방식이라 수동 배포보다 빠르고 오류가 적습니다 |
| 재사용성 | 재사용 가능한 모듈로 구성할 수 있습니다 |
| 문서화와 버전 제어 | 템플릿이 곧 문서이고, 버전 제어로 이력이 남아 롤백할 수 있습니다 |
| 검증 | 템플릿을 코드 리뷰할 수 있습니다 |

> 이 절은 교재 슬라이드 8 의 강사 노트에 있는 내용입니다. Route 53 과 직접 관련은
> 없지만, 다중 리전 장애 조치를 실제로 운영하려면 필요한 전제라서 짧게 정리했습니다.

## 4. Amazon Route 53 개요

**가용성과 확장성이 뛰어난 글로벌 DNS 웹 서비스**입니다. Route 53 은 네 가지 일을 합니다.

| 기능 | 내용 |
|---|---|
| **도메인 등록** | `example.com` 같은 도메인 이름을 등록합니다 |
| **DNS 확인** | 퍼블릭 레코드, VPC 특정 DNS 이름, 프라이빗 호스팅 영역에 대한 DNS 쿼리에 응답합니다 |
| **DNS 라우팅** | 인터넷 트래픽을 도메인의 리소스로 라우팅합니다 |
| **상태 확인** | 리소스에 자동화된 요청을 보내 도달·사용 가능 여부와 정상 작동을 확인합니다. 알림을 받고 비정상 리소스를 피해 라우팅할 수 있습니다 |

### 4.1 도메인 등록 용어 🆕

교재가 다루지 않는 구분인데, 도메인을 실제로 등록할 때 마주칩니다.

| 용어 | 의미 |
|---|---|
| **등록 대행자**(registrar) | 특정 TLD 의 도메인 등록을 처리하도록 **ICANN 이 인증**한 회사 |
| **레지스트리**(registry) | 특정 TLD 도메인을 판매할 권리를 **소유**한 회사. 예: `.com` 은 VeriSign. 해당 TLD 의 모든 도메인에 대한 권한 데이터베이스를 유지합니다 |
| **리셀러**(reseller) | 등록 대행자를 위해 도메인을 판매하는 회사. **Amazon Route 53 은 Amazon Registrar 와 등록 대행 파트너 Gandi 의 리셀러입니다** |

최상위 도메인(TLD)에는 두 종류가 있습니다.

- **일반 TLD**: `.com`, `.org`, `.bike` 등. 몇 가지 예외를 빼면 자유롭게 쓸 수 있습니다
- **지리적 TLD**: 국가·도시와 연관된 것. 일부 레지스트리는 거주 요건이 있습니다

> — 출처: [Amazon Route 53 concepts](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/route-53-concepts.html)

## 5. DNS 조회는 어떻게 이루어지는가

`www.example.com` 을 처음 입력했을 때 **몇 밀리초 안에** 벌어지는 일입니다.

```text
① 사용자 브라우저 ──────────────→ DNS 확인자 (보통 ISP 관리)
②                                    └──→ DNS 루트 네임 서버
                                          └─ ".com 네임 서버 목록" 반환
③                                    └──→ .com 최상위 도메인 네임 서버
④                                          └─ "example.com 의 Route 53 네임 서버 4개" 반환
⑤                                    └──→ Route 53 네임 서버 (하나 선택)
                                          └─ example.com 호스팅 영역에서
                                             www.example.com 레코드 조회 → 192.0.2.3
⑥ 사용자 브라우저 ←──── 192.0.2.3 ── DNS 확인자
   → HTTP/HTTPS 트래픽 시작
```

### 5.1 캐싱이 여기서 작동합니다

4단계에서 확인자는 **Route 53 네임 서버 4개를 지정된 시간 동안 캐시**합니다. 그래서
다음에 누군가 `example.com` 을 조회하면 **2단계와 3단계를 건너뜁니다.** 이미 네임 서버를
알고 있기 때문입니다.

### 5.2 재귀 쿼리와 반복적 쿼리

| 유형 | 동작 |
|---|---|
| **재귀 쿼리** | 쿼리를 받은 쪽(ISP 확인자)이 **완전한 답변을 가져와** 사용자에게 줍니다. 그 과정에서 여러 DNS 서버에 순차적으로 물어봅니다 |
| **반복적(비재귀적) 쿼리** | 완전한 답변을 가져오지 않고 **답이 있을 수 있는 다른 DNS 서버를 추천**합니다 |

🆕 그래서 **DNS 확인자를 재귀 네임 서버(recursive name server)라고도 부릅니다.**
같은 것을 가리키는 두 이름입니다.

🆕 그리고 **Route 53 네임 서버는 Route 53 을 DNS 서비스로 쓰는 모든 도메인의 권한
네임 서버(authoritative name server)** 입니다. 호스팅 영역에 만든 레코드를 기준으로
트래픽을 어떻게 라우팅할지 알고 있습니다.

> — 출처: [Amazon Route 53 concepts](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/route-53-concepts.html)

### 5.3 레코드 유형

| 레코드 | 용도 |
|---|---|
| **A** | 트래픽을 **IPv4** 주소로 라우팅 |
| **AAAA** | 트래픽을 **IPv6** 주소로 라우팅 |
| **CNAME** | 트래픽을 다른 도메인 이름으로 라우팅 |
| **MX** | 메일 서버 지정 |
| **TXT** | 이메일 발신자 확인, 애플리케이션별 값 |
| **PTR** | IP 주소를 도메인 이름에 매핑 |
| **SRV** | 서버를 식별하는 애플리케이션별 값 |

### 5.4 별칭 레코드

**별칭(alias) 레코드**는 Route 53 고유 기능입니다. **Zone Apex**(예: `example.com`)나
하위 도메인을 AWS 리소스에 직접 매핑합니다.

| 매핑할 수 있는 대상 |
|---|
| 웹 사이트 엔드포인트로 구성된 ELB 로드 밸런서 |
| Amazon CloudFront 배포 |
| Amazon S3 버킷 |

**왜 CNAME 이 아니라 별칭인가.** DNS 표준상 Zone Apex 에는 CNAME 을 쓸 수 없습니다.
`example.com` 을 로드 밸런서에 붙이려면 별칭 레코드가 필요합니다.

### 5.5 TTL 의 절충

DNS TTL 은 **Route 53 에 추가 쿼리 없이 레코드를 캐시할 수 있는 기간(초)** 을
확인자에게 알려 주는 값입니다.

| TTL | 장점 | 단점 |
|---|---|---|
| **짧게** | 레코드 업데이트를 더 빨리 반영합니다. 장애 조치가 빠릅니다 | 확인자가 더 자주 쿼리해 **쿼리 양과 비용이 늘어납니다** |
| **길게** | 확인자가 캐시로 응답해 **더 빠르고 저렴하며 때로는 더 신뢰할 수 있습니다** | 변경 반영이 느립니다 |

**절충의 축은 "지연 시간·신뢰성 ↔ 변화에 대한 대응력"** 입니다. 장애 조치를 쓰는
레코드는 TTL 을 짧게, 거의 바뀌지 않는 레코드는 길게 두는 것이 일반적인 접근입니다.

## 6. 호스팅 영역과 위임 세트

### 6.1 호스팅 영역

호스팅 영역은 **레코드를 담는 컨테이너**입니다. 특정 도메인(`example.com`)과 그 하위
도메인(`dev.example.com`, `mail.example.com`)의 트래픽을 어떻게 라우팅할지에 대한
정보를 담습니다. **호스팅 영역과 도메인의 이름은 같습니다.**

| | 퍼블릭 호스팅 영역 | 프라이빗 호스팅 영역 |
|---|---|---|
| 대상 | 외부 클라이언트 | 내부 클라이언트 |
| 확인 위치 | **인터넷을 통해** | **VPC 내부에서** |
| 라우팅 정책 | 글로벌 라우팅 정책 사용 | 대부분의 정책 사용 가능 |
| 특징 | **위임 세트**를 등록 기관·상위 도메인에 제공 | 하이브리드 네트워킹 지원, **여러 VPC 및 계정 간 연결** |
| 필요한 것 | — | **VPC 연결**, Route 53 확인자 |

> — 출처: [Working with hosted zones](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/hosted-zones-working-with.html)

### 6.2 위임 세트

도메인 이름을 등록하면 Route 53 이 **도메인과 같은 이름의 호스팅 영역**을 만듭니다.
그 안에는 DNS 쿼리를 서비스하는 **4개의 할당된 네임 서버**가 들어갑니다.
이 4개를 **위임 세트**라고 부릅니다.

```text
호스팅 영역: example.com
위임 세트:
  ns-20.awsdns-64.com
  ns-21.awsdns-65.net
  ns-22.awsdns-66.org
  ns-23.awsdns-67.co.uk
```

교재가 설명하는 동작입니다.

- AWS 는 `.com`, `.net`, `.org`, `.co.uk` 네 개의 최상위 도메인에서 호스팅되는 수천 개의
  네임 서버를 보유합니다
- 호스팅 영역을 만들 때 **각 TLD 에서 네임 서버가 무작위로 하나씩** 할당됩니다
- **위임 세트는 생성 후 수정할 수 없습니다**

**왜 서로 다른 TLD 를 섞을까요.** 한 TLD 의 네임 서버가 문제를 겪어도 나머지로 조회가
된다는 점을 생각해 보면 이해가 쉽습니다. 다만 이 해석은 AWS 문서에 명시된 설명이 아니라
구조를 보고 추론한 것입니다.

**재사용 가능한 위임 세트**(reusable delegation set)를 만들면 **둘 이상의 호스팅 영역이
같은 네임 서버 세트**를 쓸 수 있습니다. 여러 도메인을 운영할 때 등록 기관에 등록할
네임 서버를 하나로 통일할 수 있어 편합니다.

### 6.3 여러 VPC·계정에 DNS 설정 뿌리기: Route 53 Profiles 🆕

> 출시: **2024년 4월 22일** (문서 이력 기준). 교재 콘텐츠 시점보다 뒤입니다.

6.1 절 표에서 프라이빗 호스팅 영역의 특징으로 "여러 VPC 및 계정 간 연결"을 적었습니다.
VPC 가 수십 개가 되면 이 작업이 손으로 감당하기 어려워집니다. 새 VPC 를 만들 때마다
프라이빗 호스팅 영역을 연결하고, Resolver 규칙을 붙이고, DNS Firewall 규칙 그룹을
연결해야 합니다.

**Route 53 Profiles** 는 이 DNS 설정 묶음을 **하나의 객체로 만들어 여러 VPC 와 여러
계정에 적용**합니다. 문서의 표현을 옮기면 "많은 VPC 의 DNS 설정을 관리하는 일을 VPC
하나를 관리하는 것만큼 쉽게" 만드는 것이 목적입니다. **Profile 을 수정하면 연결된 모든
VPC 로 설정이 전파됩니다.**

**Profile 에 담을 수 있는 리소스**

| 리소스 | 비고 |
|---|---|
| 프라이빗 호스팅 영역과 그 안의 설정 | 6.1 절의 프라이빗 호스팅 영역 |
| Resolver 규칙 (전달 규칙과 시스템 규칙) | 하이브리드 DNS 의 핵심 |
| DNS Firewall 규칙 그룹 | 도메인 기반 필터링 |
| **인터페이스 VPC 엔드포인트** | 모듈 3 §4.2 의 그 엔드포인트입니다 |
| VPC Resolver 쿼리 로깅 구성 | 감사·문제 해결 |

**Profile 에서 직접 관리하는 VPC 구성**

- Resolver 규칙의 역방향 DNS 조회 구성
- DNS Firewall 실패 모드 구성
- DNSSEC 검증 구성

이 셋은 선택적으로 적용할 수 있습니다. 예를 들어 DNS Firewall 실패 모드는 Profile 로
통일하면서 각 VPC 의 기존 DNSSEC 검증 설정은 그대로 둘 수 있습니다.

**공유는 AWS RAM 으로** 합니다. 같은 리전의 다른 AWS 계정과 Profile 을 공유합니다.
CloudFormation 으로 새로 프로비저닝되는 VPC 에 일관된 DNS 설정을 적용할 수도 있습니다.

**VPC 하나에는 Profile 하나만** 연결할 수 있습니다.

**설정이 겹치면 무엇이 이기는가.** 마이그레이션이나 테스트 목적으로 VPC 로컬 설정과
Profile 설정을 동시에 둘 수 있습니다. 규칙은 두 단계입니다.

1. 같은 도메인 이름이면 **로컬 VPC 설정이 우선**합니다
2. 도메인 이름이 충돌하면 **더 구체적인 것이 이깁니다**

| DNS 쿼리 | Profile 규칙 | VPC 규칙 | 적용되는 규칙 |
|---|---|---|---|
| `example.com` | `example.com` | `example.com` | **로컬 VPC** |
| `test.example.com` | `test.example.com` | `example.com` | **Profile** |
| `marketing.example.com` | 없음 | `marketing.example.com` | **로컬 VPC** |

두 번째 행이 핵심입니다. Profile 쪽이 더 구체적이면 Profile 이 이깁니다.
1번 규칙만 기억하면 틀립니다.

**주의**: Profile 설정을 활성화하고 VPC 에 연결하면 **즉시 적용됩니다.**

> — 출처: [What are Amazon Route 53 Profiles?](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/profiles.html)

## 7. Route 53 상태 확인

세 가지 유형이 있습니다. **무엇을 감시하는가**로 구분하면 외우기 쉽습니다.

### 7.1 엔드포인트를 모니터링하는 상태 확인

| 항목 | 내용 |
|---|---|
| 감시 대상 | **퍼블릭 IP 주소 또는 도메인 이름** |
| 방법 | 지정한 간격으로 Route 53 이 인터넷을 통해 자동화된 요청을 애플리케이션·서버·리소스에 보냅니다 |
| 확인 내용 | 도달 가능 여부, 사용 가능 여부, 작동 여부 |
| 선택 옵션 | 특정 URL 에서 웹 페이지를 요청하는 등 **실제 사용자 요청과 비슷하게** 구성할 수 있습니다 |

### 7.2 다른 상태 확인을 모니터링하는 상태 확인 (계산된 상태 확인)

| 항목 | 내용 |
|---|---|
| 감시 대상 | **다른 상태 확인들의 상태** |
| 언제 쓰는가 | 여러 웹 서버처럼 **같은 기능을 하는 리소스가 여러 개**일 때 |
| 동작 | 각 리소스마다 알림 없는 상태 확인을 만들고, 그것들을 감시하는 상태 확인을 하나 더 만듭니다 |
| 알림 조건 | **사용 가능한 리소스 수가 지정된 임계값 아래로 떨어질 때만** 알립니다 |

서버 한 대가 죽었다고 페이지를 받고 싶지는 않지만 세 대 중 두 대가 죽으면 받고 싶은
상황을 정확히 표현할 수 있습니다.

### 7.3 CloudWatch 경보를 모니터링하는 상태 확인

| 항목 | 내용 |
|---|---|
| 감시 대상 | CloudWatch 지표를 감시하는 **경보와 같은 데이터 스트림** |
| 지표 예 | Amazon DynamoDB 의 제한된 읽기 이벤트 수, 정상으로 간주되는 ELB 호스트 수 |
| 중요한 동작 | **Route 53 은 CloudWatch 경보가 `ALARM` 상태로 전환될 때까지 기다리지 않습니다.** 데이터 스트림과 경보의 기준에 따라 상태 확인이 정상 → 비정상으로 바뀝니다 |

마지막 항목이 왜 중요한가. CloudWatch 경보는 평가 기간을 채워야 `ALARM` 으로 갑니다.
Route 53 이 그걸 기다리지 않기 때문에 **복원성과 가용성이 좋아집니다.**

## 8. 라우팅 정책

레코드를 만들 때 라우팅 정책을 고릅니다. 이것이 **Route 53 이 쿼리에 응답하는 방식**을
결정합니다.

### 8.1 8가지 정책

| 정책 | 언제 쓰는가 |
|---|---|
| **단순**(Simple) | 도메인에 대해 특정 기능을 하는 리소스가 **하나**일 때 |
| **장애 조치**(Failover) | **액티브-패시브** 장애 조치를 구성할 때 |
| **지리적 위치**(Geolocation) | **사용자의 위치**를 기준으로 라우팅할 때 |
| **지리적 근접성**(Geoproximity) | **리소스의 위치**를 기준으로 라우팅하고, 선택적으로 한 위치에서 다른 위치로 트래픽을 옮길 때 |
| **지연 시간 기반**(Latency) | 여러 AWS 리전의 리소스 중 **왕복 시간이 가장 짧은** 리전으로 보낼 때 |
| **IP 기반**(IP-based) | 사용자 위치 기준으로 라우팅하면서 **트래픽이 발생한 IP 주소를 보유**할 때 |
| **다중값 응답**(Multivalue answer) | Route 53 이 무작위로 선택된 **최대 8개의 정상 레코드**로 응답하게 할 때 |
| **가중치**(Weighted) | 트래픽을 **지정한 비율**로 여러 리소스에 나눌 때 |

🆕 이 정책들 대부분은 **프라이빗 호스팅 영역에서도** 레코드를 만들 수 있습니다.
문서가 프라이빗 호스팅 영역 지원을 명시하지 않은 것은 IP 기반 정책입니다.

> — 출처: [Choosing a routing policy](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/routing-policy.html)

**지리적 위치와 지리적 근접성의 차이**가 자주 헷갈립니다. 지리적 위치는 **사용자가
어디 있는지**를 보고, 지리적 근접성은 **리소스가 어디 있는지**를 봅니다. 후자는
바이어스 값으로 특정 리소스가 커버하는 지리적 범위를 넓히거나 좁힐 수 있습니다.

🆕 IP 기반 라우팅에 쓰는 CIDR 블록은 **IPv4 는 `/0`\~`/24`, IPv6 는 `/0`\~`/48`** 까지
지정할 수 있습니다. CIDR 블록을 **CIDR 로케이션**으로 묶고, 이를 다시
**재사용 가능한 CIDR 컬렉션**으로 묶어 관리합니다.

### 8.2 단순 라우팅

가중치나 지연 시간 같은 특별한 처리 없이 **표준 DNS 레코드**를 구성합니다. 보통
리소스 하나로 트래픽을 보냅니다.

```text
DNS 쿼리 → Route 53 → us-east-1 의 ELB → Auto Scaling 그룹
```

실습 3 에서 먼저 이것을 구성하고 DNS 확인을 테스트한 뒤, 고급 정책으로 넘어갑니다.
**동작하는 기준선을 먼저 만드는 것**이 순서입니다.

### 8.3 장애 조치 라우팅

**액티브-패시브** 구성입니다. Route 53 상태 확인이 리소스의 상태와 성능을 감시하고,
기본 리소스가 비정상이면 보조 리소스로 보냅니다.

```text
[정상]   DNS 쿼리 → Route 53 → us-east-1 ELB → ASG   ✓
                              (eu-west-2 는 대기)

[장애]   DNS 쿼리 → Route 53 ─✗ us-east-1 ELB → ASG   ✗ 상태 확인 실패
                              → eu-west-2 ELB → ASG   ✓ 전환
```

**상태 확인 없이는 장애 조치가 동작하지 않습니다.** 7장과 이 정책은 한 쌍입니다.

### 8.4 지연 시간 기반 라우팅

여러 리전의 리소스에 대해 **지연 시간 레코드**를 만들어 둡니다. Route 53 은 쿼리를 받으면
어떤 리전에 레코드가 있는지 확인하고, **사용자에게 지연 시간이 가장 짧은 리전**의 레코드를
골라 응답합니다.

```text
example.com 의 DNS 쿼리 → Amazon Route 53
                            ├─ us-east-1 : 137밀리초
                            └─ eu-west-2 :  76밀리초   ← 선택
```

**주의할 점이 두 가지 있습니다.**

- 지연 시간 데이터는 **사용자와 AWS 데이터 센터 간 트래픽에 전적으로 기반**합니다.
  AWS 리전에서 리소스를 쓰지 않으면 실제 지연 시간이 AWS 데이터와 크게 다를 수
  있습니다. **리소스가 AWS 리전과 같은 도시에 있어도** 마찬가지입니다
- 표시되는 지연 시간은 **클라이언트 서브넷 또는 확인자 뒤의 클라이언트와 리전 간의
  샘플링된 데이터** 기반입니다

즉 지연 시간 기반 라우팅은 "**AWS 가 측정한** 지연 시간"으로 판단합니다. 내가 측정한
값과 다를 수 있다는 것을 알고 써야 합니다.

### 8.5 정책 고르기

| 원하는 것 | 정책 |
|---|---|
| 리소스가 하나뿐이다 | 단순 |
| 기본과 백업을 두고 자동 전환하고 싶다 | **장애 조치** |
| 사용자에게 가장 빠른 리전으로 보내고 싶다 | **지연 시간 기반** |
| 특정 국가 사용자를 특정 엔드포인트로 보내야 한다 (규정 준수, 현지화) | 지리적 위치 |
| 리소스 위치 기준으로 커버 범위를 조절하고 싶다 | 지리적 근접성 |

## 9. 실습 3: 내결함성과 글로벌 트래픽 최적화

소요 시간 30분. 상세 절차는 실습 가이드를 따르세요.

### 9.1 실습 태스크

1. 고가용성과 비즈니스 연속성을 위한 **다중 리전 내결함성의 중요성** 설명
2. 여러 리전에서 내결함성·고가용성을 보장하기 위한 **네트워킹 구성과 정책 평가·선택**
3. 트래픽 흐름, 지연 시간 기반 라우팅, 지리적 위치 라우팅 같은 **Route 53 고급 기능** 설명
4. 지연 시간·지리·상태 확인을 기반으로 여러 지역에 **트래픽을 지능적으로 분산**
5. 다중 리전 배포의 **중복성과 단일 네트워크 장애 지점을 테스트·검증**.
   오류를 시뮬레이션하고 정상 리전으로 자동 리디렉션되는지 확인

### 9.2 수행 순서

1. Route 53 호스팅 영역 추가 (`example.com`)
2. **단순 라우팅 정책** 구성
3. 단순 라우팅 정책에 대한 **DNS 확인 테스트**
4. **고급 라우팅 정책** 구성 (장애 조치 및 지연 시간)
5. 고급 라우팅 정책에 대한 **DNS 확인 테스트**

### 9.3 아키텍처

```text
[시작]  사용자 ──→ 리전 A: ALB → Auto Scaling 그룹 → Aurora
        사용자 ──→ 리전 B: ALB → Auto Scaling 그룹 → Aurora
                    (사용자가 각 리전의 ALB 로 직접 접근)

[완성]  사용자 ──→ Amazon Route 53 ──┬──→ 리전 A: ALB → ASG → Aurora
                    │                └──→ 리전 B: ALB → ASG → Aurora
                    └─ 각 리전에 상태 확인
```

**무엇이 달라지는가.** 시작 상태에서는 사용자가 어느 리전으로 가야 하는지 스스로
알아야 하고, 한 리전이 죽으면 그 리전을 쓰던 사용자는 서비스를 못 씁니다.
완성 상태에서는 Route 53 이 **상태 확인 결과와 지연 시간을 보고** 대신 결정합니다.

> 실습에 쓰이는 두 리전은 교재 내에서 표기가 엇갈립니다. 모듈 4 다이어그램은
> `us-east-1` 과 `ap-northeast-1`, 모듈 5 의 실습 요약은 미국과 영국으로 적혀 있습니다.
> 실제 리전은 실습 환경에서 확인하세요.

### 9.4 ExampleCorp 의 결론

- Amazon Route 53 을 글로벌 DNS 서비스로 통합하고 `example.com` 도메인을 등록했습니다
- 리전 간 중복성을 위해 라우팅 정책을 구현했습니다
- Terry 는 오류를 시뮬레이션해 리소스와 트래픽이 정상 리전으로 자동 리디렉션되는지
  꼼꼼히 테스트했습니다

### 자주 틀리는 것

| 오해 | 사실 |
|---|---|
| 장애 조치 정책만 만들면 전환된다 | 상태 확인이 있어야 동작합니다 |
| Zone Apex 에 CNAME 을 쓸 수 있다 | 쓸 수 없습니다. 별칭 레코드를 씁니다 |
| TTL 은 짧을수록 좋다 | 쿼리 양과 비용이 늘어납니다. 용도별로 정합니다 |
| 지연 시간 기반 라우팅은 내 측정값을 쓴다 | AWS 가 측정한 사용자↔AWS 데이터 센터 지연 시간을 씁니다 |
| 프라이빗 호스팅 영역은 단순 라우팅만 된다 | 대부분의 정책을 쓸 수 있습니다 |
| 위임 세트는 나중에 바꿀 수 있다 | 생성 후 수정할 수 없습니다 |
| Profile 과 VPC 설정이 겹치면 항상 VPC 가 이긴다 | 같은 도메인이면 VPC 가 이기지만, **더 구체적인 쪽이 우선**입니다 |
| VPC 에 Profile 을 여러 개 붙일 수 있다 | VPC 하나에 Profile 하나입니다 |
| 지리적 위치와 지리적 근접성은 같다 | 전자는 사용자 위치, 후자는 리소스 위치 기준입니다 |
| 다중값 응답은 로드 밸런서 대체다 | 상태 확인된 레코드를 최대 8개 무작위로 돌려주는 DNS 기능입니다. 로드 밸런싱 알고리즘이 아닙니다 |
