## 1. 과정 개요

### 1.1 수강 전 권장 사항

| 항목 | 내용 |
|---|---|
| 선행 과정 | **AWS Technical Essentials** 또는 **Cloud Practitioner Essentials** |
| 선행 지식 | 네트워킹 개념과 AWS 서비스에 대한 기본 지식 |
| 추가 권장 | 3일 과정 **Architecting on AWS** 를 함께 들으면 설계 기초를 다지는 데 도움이 됩니다 |

### 1.2 과정 목표

이 과정을 마치면 다음을 할 수 있습니다.

1. 다양한 네트워킹 서비스 간의 **설계 장단점을 고려**하여 확장 가능한 프로덕션
   애플리케이션의 네트워킹 인프라를 **설계**합니다
2. 가용성이 뛰어나고 탄력적이며 확장 가능한 애플리케이션을 위한 네트워킹 서비스를
   **구성**합니다
3. 변화하는 비즈니스 요구 사항에 따라 네트워킹 인프라를 **구현**합니다
4. **AWS Well-Architected Framework** 에 맞게 네트워킹 모범 사례를 구현합니다

목표 문장에서 눈여겨볼 단어는 **"설계 장단점(design trade-offs)"** 입니다. 이 과정은
"이 서비스가 최고다"를 배우는 과정이 아니라 **언제 무엇을 고르는가**를 배우는 과정입니다.

## 2. ExampleCorp의 여정

이 과정의 모든 모듈은 하나의 회사 사례를 따라갑니다. 개념을 배울 때마다
"ExampleCorp 의 어떤 문제를 푸는가"로 연결되므로, 여기서 상황을 정확히 잡아 두면
나머지가 쉬워집니다.

### 2.1 ExampleCorp 의 상황

**지금까지 온프레미스 네트워킹만으로 운영해 온 글로벌 회사**입니다. IT 비용이
증가하고 빠르게 크기를 조정할 수 없어 클라우드 옵션을 찾고 있습니다.

| 현재 상태 | 내용 |
|---|---|
| 비용 | IT 및 데이터 센터 비용 증가에 대한 **경영진의 우려** |
| 인력 | 전 세계에 분산된 직원 |
| 레거시 | **IPv4 를 사용하여 설계된 레거시 애플리케이션**을 계속 지원해야 함 |
| 규정 | 연방 계약 지원 → **연방 정부의 IPv6 의무화** 준수 필요 |

**중요한 전제**: ExampleCorp 는 운영을 클라우드로 **전부 마이그레이션한 것이 아닙니다.**
클라우드 운영 가능성을 시험하기 위해 **웹 애플리케이션 하나를 배포**했습니다.

### 2.2 Terry 를 소개합니다

| 항목 | 내용 |
|---|---|
| 역할 | ExampleCorp 의 **DevOps 엔지니어**. IT 부서가 AWS 클라우드 프로젝트를 구현하기로 결정 |
| 왜 AWS 인가 | AWS 인프라의 성숙도와 사용 가능한 서비스의 폭 |
| 강점 | 네트워킹에 대한 **광범위한 기존 지식** |
| 약점 | 3티어 웹 애플리케이션을 **AWS 클라우드에 배포하는 전문 지식**이 부족했습니다 |
| 결과 | 기존 지식으로 "리프트 앤 시프트"를 수행했고, 그 결과 초기 설정에 **신뢰성·안정성·확장성·비용 최적화가 부족**합니다 |

Terry 의 상황이 이 과정의 대상 수강생과 비슷하다는 점이 포인트입니다. **네트워킹을 아는
사람이 AWS 네트워킹을 배울 때 무엇을 놓치는지**를 사례로 보여 줍니다.

### 2.3 Terry 의 초기 설계

```text
AWS 클라우드 / 리전
└─ VPC  10.1.0.0/22
   ├─ 인터넷 게이트웨이
   ├─ 퍼블릭 서브넷 ── Auto Scaling 그룹 (웹 서버)
   ├─ 프라이빗 서브넷 ── Aurora
   └─ 프라이빗 서브넷 ── Aurora
```

이 다이어그램만 보고 문제점을 몇 개 찾을 수 있는지 세어 보세요. 모듈 1을 읽고 나면
전부 보입니다.
