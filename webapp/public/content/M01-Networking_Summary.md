## 2. IP 주소 지정 기초

### 2.1 CIDR 표기법 (IPv4)

CIDR 표기법은 **IP 주소 + 네트워크 마스크**를 한 번에 쓰는 방법입니다.

```text
10.22.0.0/16
└──┬───┘ └┬┘
   │      └─ 슬래시 표기법: 네트워크 식별에 쓰는 비트 수
   └──────── 점 표기법: 네트워크 또는 서브넷
```

IPv4 주소는 8비트 4개 그룹, 총 32비트입니다. `/16` 이면 앞 16비트가 네트워크 식별용으로
고정되고, 남은 16비트가 호스트 범위가 됩니다.

```text
10.22.0.0/16 → 00001010.00010110.00000000.00000000
               └──── 네트워크 ────┘└──── 호스트 ─────┘

호스트 범위: 10.22.0.0 ~ 10.22.255.255  (65,536개)
```

VPC 에서 쓸 수 있는 크기별 주소 수입니다. 넷마스크 숫자가 1 줄어들면 주소 수는 2배가
됩니다.

| CIDR | 총 IP 수 |
|---|---|
| `/28` | 16 |
| … | … |
| `/20` | 4,096 |
| `/19` | 8,192 |
| `/18` | 16,384 |
| `/17` | 32,768 |
| `/16` | 65,536 |

> 서브넷 계산이 낯설면 넷마스크를 "고정된 비트 수"로 읽는 습관을 들이세요.
> `/24` 는 마지막 옥텟만 자유롭다는 뜻이고, 그래서 256개입니다.

### 2.2 CIDR 표기법 (IPv6)

IPv6 주소는 **128비트**입니다. 16비트씩 **8개 그룹**으로 끊고, 각 그룹을 16진수 4자리로
적습니다. 그룹 사이 구분자는 콜론(`:`)입니다.

```text
2001:0db8:1234:0001:0000:8a2e:0370:7334
└──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘ └──┘
 1    2    3    4    5    6    7    8     ← 그룹 8개, 각 16비트
```

그대로 쓰면 너무 길어서 **줄여 쓰는 규칙이 두 가지** 있습니다.

**규칙 1 — 그룹 앞쪽의 0 은 지웁니다.** 그룹 안에서 앞자리에 붙은 0 만 해당합니다.

```text
0db8 → db8      0001 → 1      0000 → 0
```

**규칙 2 — 값이 전부 0 인 그룹이 연달아 나오면 `::` 로 한꺼번에 지웁니다.**
`::` 는 **한 주소에 한 번만** 쓸 수 있습니다.

두 규칙을 차례로 적용하면 이렇게 됩니다.

```text
원래 주소     2001:0db8:1234:0000:0000:0000:0370:7334
규칙 1 적용   2001:db8:1234:0:0:0:370:7334
규칙 2 적용   2001:db8:1234::370:7334
```

`::` 를 한 번만 허용하는 이유는 **되돌릴 수 있어야 하기 때문**입니다. `::` 가 두 번 나오면
지워진 0 그룹이 어느 쪽에 몇 개씩 있었는지 알 수 없습니다. 한 번뿐이면 계산이 됩니다.
위 결과에는 그룹이 5개 남았으니 `::` 가 감춘 그룹은 `8 - 5 = 3개` 입니다.

**0 인 그룹이 하나뿐일 때는 `::` 를 쓰지 않고 `0` 으로 둡니다.** 규칙 2 는 "연달아"에만
해당하고, 하나를 `::` 로 바꾸면 오히려 몇 개를 지웠는지 헷갈립니다
([RFC 5952](https://datatracker.ietf.org/doc/html/rfc5952) 4.2.2 절도 이를 금지합니다).

```text
2001:0db8:1234:0001:0000:8a2e:0370:7334   ← 0 인 그룹이 5번째 하나뿐
2001:db8:1234:1:0:8a2e:370:7334           ← 그래서 `::` 가 아니라 `0`
```

**IPv6 CIDR 표기도 이 규칙의 결과입니다.** AWS 문서는 IPv6 CIDR 블록을 "끝이 전부 0 인
그룹으로 끝나는 주소에서 그 부분을 `::` 로 바꾸고, 뒤에 슬래시와 0\~128 사이 숫자를 붙인 것"
으로 설명합니다. 그래서 VPC 에 할당되는 CIDR 이 아래처럼 생깁니다.

```text
2001:db8:1234:1a00::/56
                └┘ └─┘
                │   └── 앞에서 고정된 비트 수
                └────── 뒤쪽 전부 0 인 그룹들을 :: 로 줄인 것
```

`::` 를 풀어 쓰면 이렇게 됩니다. 앞에 적힌 그룹이 `2001`, `db8`, `1234`, `1a00` 네 개이므로
`::` 가 감춘 그룹은 `8 - 4 = 4개` 입니다.

```text
2001:db8:1234:1a00::/56
= 2001:0db8:1234:1a00:0000:0000:0000:0000/56
```

여기서 한 가지 헷갈리는 점이 있습니다. **`/56` 의 경계는 그룹 중간에 걸립니다.**
한 그룹이 16비트이므로 56비트는 세 그룹(48비트)에 8비트를 더한 값입니다.

```text
그룹    1      2      3      4        5      6      7      8
      2001   0db8   1234   1a 00    0000   0000   0000   0000
비트    16     16     16    8 + 8     16     16     16     16
       ●      ●      ●     ● ○      ○      ○      ○      ○

● 고정 (합 56비트)      ○ 자유 (합 72비트)
```

그룹 4 의 앞 절반 `1a` 까지가 고정이고 뒤 절반 `00` 은 자유입니다. 그래서 이 블록이 담는
주소의 범위는 이렇게 됩니다.

```text
처음   2001:0db8:1234:1a00:0000:0000:0000:0000
마지막 2001:0db8:1234:1aff:ffff:ffff:ffff:ffff
```

자유 비트가 `8 + 64 = 72` 개이므로 주소 수는 2^72 개입니다. 같은 계산을
`128 - 56 = 72` 로 바로 해도 됩니다. **위의 범위와 개수는 AWS 문서가 같은 예로 적어 둔
값입니다.**

이 `/56` 안에는 `/64` 서브넷을 `2^(64-56) = 256` 개 만들 수 있습니다. 4장에서 볼 서브넷
예시 `...1a00::/64`, `...1a01::/64`, `...1a02::/64`, `...1a03::/64` 가 그 256개 중 넷입니다.
그룹 4 의 뒤 절반이 `00`, `01`, `02`, `03` 으로 움직이는 것이 보입니다.

> — 출처: [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html)

### 2.3 IPv4 와 IPv6 비교

| 특징 | IPv4 | IPv6 |
|---|---|---|
| 길이 | 32비트 (8비트 4개 그룹) | 128비트 (16비트 8개 그룹) |
| 주소 수 | 2^32 ≈ 43억 | 2^128 ≈ 3.4 × 10^38 |
| 표기 | 점으로 구분된 10진수 | 콜론으로 구분된 16진수 |
| 예 | `192.168.10.10` | `2001:db8:1234:1a00::1` |
| 프라이빗 공간 | RFC 1918 범위 | 고유 로컬 주소(ULA) `fc00::/7` — AWS 에서 쓰는 범위는 `fd80::/9` |
| 퍼블릭 주소 | ICANN 할당 | 글로벌 유니캐스트(GUA) `2000::/3` |
| 루프백 | `127.0.0.1` | `::1/128` |

#### 퍼블릭 주소를 "GUA `2000::/3` 에서 할당한다"는 말의 뜻

표의 `2000::/3` 은 특정 주소가 아니라 **주소 블록**입니다. `/3` 이니까 앞 3비트만 고정입니다.

```text
2000::/3  →  앞 3비트가 001 인 주소 전부

첫 주소  2000:0000:0000:0000:0000:0000:0000:0000
끝 주소  3fff:ffff:ffff:ffff:ffff:ffff:ffff:ffff
```

16진수 첫 자리가 `2` 또는 `3` 이면 이 안에 있습니다. 앞에서 본 `2001:db8:1234:1a00::/56` 도
`2` 로 시작하므로 여기에 속합니다. 자유 비트가 `128 - 3 = 125` 개이므로 크기는 2^125 개,
전체 IPv6 공간의 **8분의 1** 입니다.

IANA 는 이 블록을 **글로벌 유니캐스트**(전 세계에서 유일하고 인터넷으로 라우팅되는 주소)로
지정하고, 현재 유니캐스트 주소 할당을 이 범위로 한정하고 있습니다. IPv6 유니캐스트 공간
자체는 멀티캐스트 `ff00::/8` 을 뺀 전 범위이지만, **실제로 나눠 주는 것은 `2000::/3` 안**
입니다. 이 지정은 AWS 가 아니라 IANA 의 것입니다
(참고: [IANA IPv6 Address Space](https://www.iana.org/assignments/ipv6-address-space/ipv6-address-space.xhtml)).

주소는 위에서 아래로 쪼개져 내려옵니다.

```text
IANA  →  지역 인터넷 레지스트리  →  AWS 같은 조직  →  내 VPC(/56)  →  서브넷(/64)  →  인스턴스
```

**그래서 "GUA 에서 퍼블릭 주소를 할당한다"는 말은, 내 VPC 의 IPv6 CIDR 이 전 세계에서 유일한
그 블록의 한 조각이라는 뜻입니다.** IPv4 처럼 `10.0.0.0/16` 을 내 마음대로 정해 쓰고 NAT 로
바꿔서 나가는 방식이 아니라, **처음부터 인터넷에서 통하는 주소를 받아 오는 것**입니다.
그래서 VPC 의 IPv6 CIDR 은 사용자가 직접 고를 수 없고 Amazon 풀에서 받습니다(3.2 절).

AWS 문서는 이 성질을 이렇게 적습니다. Amazon 이 제공하는 IPv6 주소는 **항상 인터넷에
광고되며, 전 세계에서 유일하므로 인터넷에서 도달 가능**합니다. 도달 여부는 주소 자체가
아니라 서브넷의 라우팅(7장)과 보안 그룹·네트워크 ACL(9장)로 통제합니다.

> — 출처: [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html)

#### IPv6 에도 프라이빗 주소가 있습니다 🔄

**교재는 이 내용을 같은 슬라이드 안에서 다르게 설명합니다.** 슬라이드 10 의 표에는 IPv6 의
프라이빗 공간이 고유 로컬 주소 `fc00::/7` 이라고 적혀 있는데, 같은 슬라이드의 강사 노트에는
"IPv6 에는 IPv4 와 같이 프라이빗 주소 범위가 할당되지 않는다" 고 적혀 있습니다.
**표 쪽이 맞습니다.** 고유 로컬 주소(ULA, Unique Local Address)는
[RFC 4193](https://datatracker.ietf.org/doc/html/rfc4193)이 정의한 IPv6 의 프라이빗 주소
공간이고, IPv4 의 RFC 1918 에 대응하는 개념입니다.

AWS 문서도 **퍼블릭 IPv6 와 프라이빗 IPv6 를 모두 지원한다**고 명시합니다. AWS 의 구분
기준은 주소 형태가 아니라 **"AWS 가 그 주소를 인터넷으로 광고하는가"** 입니다.

| 구분 | 범위 | 인터넷 광고 | 비고 |
|---|---|---|---|
| 퍼블릭 IPv6 | 글로벌 유니캐스트 `2000::/3` | 광고됨 | Amazon 제공 범위 또는 본인 소유 범위(BYOIP) |
| 프라이빗 IPv6 — ULA | 고유 로컬 주소 (범위는 바로 아래 표) | 광고되지 않음 | RFC 4193 |
| 프라이빗 IPv6 — GUA | 본인이 소유한 글로벌 유니캐스트 범위 | 광고되지 않음 | **기본 비활성.** IPAM 에서 먼저 켜야 씁니다 |

**ULA 범위는 문서마다 다른 값으로 보입니다.** 표준이 정의한 블록과 AWS 가 실제로 허용하는
범위가 다르기 때문입니다. 넷을 구분해 두면 헷갈리지 않습니다.

| 계층 | 범위 | 설명 |
|---|---|---|
| RFC 4193 이 정의한 ULA 전체 | `fc00::/7` | 이 접두사가 "고유 로컬 유니캐스트"를 뜻합니다. 교재 표에 적힌 값입니다 |
| 그중 할당 방식이 정의된 절반 | `fd00::/8` | RFC 4193 의 `L` 비트가 1, 즉 **로컬 할당**입니다. `L` 이 0 인 `fc00::/8` 은 "나중에 정의될 수 있다"고만 되어 있어 실제로 쓰지 않습니다 |
| AWS 에서 유효한 ULA | `fd00::/8` 에서 Amazon 예약 범위 `fd00::/16` 을 뺀 부분 | 예약 범위와 겹치는 CIDR 은 쓸 수 없습니다 |
| AWS IPAM 에 프로비저닝 가능 | `fd80::/9`, 크기는 `/9` \~ `/60` | 실무에서 실제로 고르는 범위입니다 |

정리하면 **표준 답은 `fc00::/7`, 실무 답은 `fd80::/9`** 입니다. 시험에서 "IPv6 의 프라이빗
주소 공간"을 물으면 `fc00::/7` 이고, 콘솔에서 IPAM 풀을 만들 때 넣는 값은 `fd80::/9` 아래의
CIDR 입니다.

프라이빗 IPv6 를 쓸 때 알아 둘 점입니다.

- **IPAM 을 통해서만 쓸 수 있습니다.** VPC 에 프라이빗 IPv6 CIDR 을 직접 적어 넣는 방식이
  아니라, IPAM 풀에서 할당받습니다.
- **인터넷 게이트웨이나 송신 전용 인터넷 게이트웨이가 있어도 인터넷으로 나가지 못합니다.**
  프라이빗 IPv6 트래픽은 인터넷 게이트웨이 경계에서 폐기됩니다. 나가야 한다면 퍼블릭 IPv6
  주소를 가진 다른 서브넷의 리소스를 거쳐야 합니다.
- Direct Connect, VPC 피어링, Transit Gateway, VPN 을 통한 통신은 지원됩니다.
- 서브넷의 처음 4개와 마지막 1개 주소는 AWS 가 예약합니다. IPv4 와 같습니다(4.2 절).
- 프라이빗 IPv6 주소에는 요금이 없습니다.

그래서 **"IPv6 는 무조건 퍼블릭" 으로 외우면 안 됩니다.** 다만 Amazon 이 제공하는 IPv6 CIDR
블록은 글로벌 유니캐스트이고 인터넷에 광고되므로, 별도 설정 없이 만든 듀얼 스택 VPC 에서는
IPv6 주소가 퍼블릭인 것이 맞습니다. IPv6 에 IPv4 식의 주소 절약용 NAT 가 없다는 교재 설명도
맞습니다. 아웃바운드만 허용하려면 **송신 전용 인터넷 게이트웨이**(8장)를 씁니다.

> — 출처: [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html)

### 2.4 RFC 1918 프라이빗 IPv4 범위 🔄

VPC 를 만들 때 AWS 는 RFC 1918 프라이빗 범위에서 CIDR 을 고르라고 권장합니다.

| RFC 1918 범위 | 실제 주소 범위 | VPC CIDR 예 |
|---|---|---|
| `10.0.0.0/8` | `10.0.0.0` \~ `10.255.255.255` | `10.0.0.0/16` |
| `172.16.0.0/12` | `172.16.0.0` \~ **`172.31.255.255`** | `172.31.0.0/16` |
| `192.168.0.0/16` | `192.168.0.0` \~ `192.168.255.255` | `192.168.0.0/20` |

**교재의 강사 노트는 `172.16.0.0/12` 의 끝 주소를 `172.16.31.255` 로 적었습니다.
이는 틀렸습니다.** `/12` 는 두 번째 옥텟의 앞 4비트까지 고정하므로 두 번째 옥텟이
16부터 31까지 움직입니다. 따라서 범위 끝은 `172.31.255.255` 입니다. 자주 나오는
`172.31.0.0/16`(기본 VPC 의 CIDR)이 이 범위 안에 들어간다는 점으로도 확인할 수 있습니다.

> — 출처: [VPC CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html)

### 2.5 AWS 가 게시하는 IP 주소 범위 🆕

AWS 는 자사가 쓰는 모든 IP 주소 범위를 JSON 파일로 공개합니다. 방화벽 허용 목록을
만들거나 특정 서비스의 범위를 확인할 때 씁니다.

```bash
# AWS 공개 IP 주소 범위 내려받기
curl -O https://ip-ranges.amazonaws.com/ip-ranges.json
```

> — 출처: [AWS IP address ranges](https://docs.aws.amazon.com/vpc/latest/userguide/aws-ip-ranges.html)

## 3. Amazon VPC 기본 사항

### 3.1 VPC 란

Amazon VPC 는 AWS 계정 안에 만드는 **논리적으로 격리된 가상 네트워크**입니다.
자체 데이터 센터의 네트워크와 개념이 거의 같습니다.

| 성질 | 내용 |
|---|---|
| 범위 | **단일 리전**. 고가용성을 원하면 VPC 안에서 여러 가용 영역에 걸쳐 서브넷을 만듭니다 |
| 주소 | IPv4 CIDR 은 **필수**, IPv6 CIDR 은 선택 |
| 구성 | 서브넷, 라우팅 테이블, 게이트웨이, 보안 그룹, 네트워크 ACL |

### 3.2 CIDR 크기와 개수

| 항목 | 값 |
|---|---|
| IPv4 CIDR 크기 | `/16`(65,536개) \~ `/28`(16개) |
| IPv4 CIDR 블록 수 | 기본 **5개**, 최대 **50개**까지 조정 가능 (기본 CIDR + 모든 보조 CIDR 포함) |
| IPv6 CIDR 블록 수 | 최대 **5개**. `/44` \~ `/60` 을 `/4` 단위로 |
| IPv6 CIDR 크기 | **Amazon 제공은 `/56` 고정.** 크기를 고르려면 IPAM 이나 BYOIP 로 직접 가져와야 합니다 |
| 리전당 VPC | 기본 **5개**, 조정 가능 |
| VPC당 서브넷 | 기본 **200개**, 조정 가능 |

IPv6 CIDR 크기를 헷갈리기 쉬운 지점입니다. **연결할 수 있는 크기의 범위**와 **Amazon 이
주는 크기**는 다릅니다.

| 어떻게 받는가 | 크기 |
|---|---|
| **Amazon 제공 IPv6 CIDR 블록** (콘솔에서 이 옵션 선택) | **`/56` 고정.** 범위도 사용자가 고를 수 없습니다 |
| IPAM 풀에서 할당 / 본인 소유 범위(BYOIP) | `/44` \~ `/60` 을 `/4` 단위로 |

> — 출처: [Add or remove a CIDR block from your VPC](https://docs.aws.amazon.com/vpc/latest/userguide/add-ipv4-cidr.html)

**VPC 에 지정할 수 없는 CIDR 블록** 🆕

| 블록 | 이유 |
|---|---|
| `0.0.0.0/8` | 예약 |
| `127.0.0.0/8` | 내부 호스트 루프백 |
| `169.254.0.0/16` | 링크-로컬 |
| `224.0.0.0/4` | 멀티캐스트 |

`172.17.0.0/16` 은 금지 목록은 아니지만 **일부 AWS 서비스가 내부적으로 사용**하므로
피하는 것이 좋습니다. 겹치면 IP 충돌이 발생할 수 있습니다.

> — 출처: [VPC CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html)

### 3.3 CIDR 은 나중에 늘릴 수 있지만, 줄이거나 바꿀 수는 없습니다

교재에서 Terry 가 겪은 문제가 바로 이것입니다. `/22`(1,024개)로 만든 VPC 는 나중에
`/16` 으로 "확대"할 수 없습니다.

| 하고 싶은 것 | 가능한가 |
|---|---|
| 기본(primary) CIDR 블록 변경 | ❌ 불가 |
| 기본 CIDR 블록 연결 해제 | ❌ 불가 |
| 기존 CIDR 블록 크기 확대·축소 | ❌ 불가 |
| **보조(secondary) IPv4 CIDR 블록 추가** | ✅ 가능 |
| 다른 CIDR 로 새 VPC 를 만들고 마이그레이션 | ✅ 가능 (다만 큰 작업) |

보조 CIDR 을 연결하면 라우팅 테이블에 **로컬 경로가 자동으로 추가**됩니다.

| 대상 위치 | 대상 |
|---|---|
| `10.0.0.0/16` | `local` |
| `10.2.0.0/16` | `local` |

그렇다고 처음부터 아주 큰 블록을 잡는 것도 답이 아닙니다. 다른 VPC 나 온프레미스
네트워크와 겹치면 나중에 VPC 피어링(모듈 3)을 못 하게 됩니다. **성장 계획을 세우고
겹치지 않게 잡는 것**이 핵심입니다.

> — 출처: [VPC CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html)

### 3.4 기본 VPC 와 사용자 지정 VPC

계정에는 리전마다 **기본 VPC** 가 하나 있습니다. 바로 인스턴스를 띄울 수 있도록 각 AZ 의
퍼블릭 서브넷, 인터넷 게이트웨이, DNS 확인 설정이 미리 구성되어 있습니다.

기본 VPC 의 전형적인 구성입니다.

| 리소스 | CIDR |
|---|---|
| VPC | `172.31.0.0/16` |
| 기본 서브넷 (AZ 별) | `172.31.0.0/20`, `172.31.16.0/20`, `172.31.32.0/20` … |

기본 라우팅 테이블:

| 대상 위치 | 대상 |
|---|---|
| `172.31.0.0/16` | `local` |
| `0.0.0.0/0` | 인터넷 게이트웨이 ID |

**프로덕션에는 사용자 지정 VPC 를 씁니다.** 리전당 기본 VPC 는 1개뿐이고, 주소 범위와
서브넷 구성을 요구 사항에 맞게 정할 수 없기 때문입니다.

사용자 지정 VPC 배포 순서:

1. **계획** — 향후 확장성과 유연성을 먼저 생각합니다
2. **IP 주소 범위 정의** — 기존 네트워크·다른 VPC 와 겹치지 않게
3. **서브넷 생성** — 서로 다른 가용 영역에
4. **라우팅 테이블 구성** — 퍼블릭용과 프라이빗용을 나눠서
5. **게이트웨이 설정** — 인터넷 게이트웨이 또는 NAT 게이트웨이

### 3.5 듀얼 스택 VPC

VPC 는 IPv4 와 IPv6 를 동시에 쓰는 **듀얼 스택 모드**로 동작할 수 있습니다. 두 통신은
서로 **독립적**입니다. IPv4 경로가 있어도 IPv6 경로는 따로 만들어야 합니다.

```text
VPC   10.0.0.0/16  +  2001:db8:1234:1a00::/56
├─ AZ 1
│   ├─ 퍼블릭 서브넷   10.0.0.0/24  + 2001:db8:1234:1a00::/64
│   └─ 프라이빗 서브넷 10.0.2.0/24  + 2001:db8:1234:1a02::/64
└─ AZ 2
    ├─ 퍼블릭 서브넷   10.0.1.0/24  + 2001:db8:1234:1a01::/64
    └─ 프라이빗 서브넷 10.0.3.0/24  + 2001:db8:1234:1a03::/64
```

**중요: VPC 의 IPv4 지원은 끌 수 없습니다.** AWS 문서는 "VPC 에는 반드시 IPv4 CIDR
블록이 연결되어 있어야 한다"고 명시합니다. 즉 **IPv6 전용 VPC 는 만들 수 없습니다.**
다만 듀얼 스택 VPC 안에 **IPv6 전용 서브넷**은 만들 수 있습니다. 교재 기술이 현재도
맞습니다.

> — 출처: [VPC CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html)

## 4. 서브넷

### 4.1 서브넷의 성질

| 성질 | 내용 |
|---|---|
| 범위 | **하나의 가용 영역 안에만** 존재. AZ 를 걸칠 수 없습니다 |
| 개수 | 하나의 AZ 에 여러 서브넷을 둘 수 있습니다 |
| CIDR | VPC CIDR 의 부분집합. 서브넷끼리 겹칠 수 없습니다 |
| IPv4 크기 | `/28` \~ `/16` |
| IPv6 크기 | `/44` \~ `/64` 를 `/4` 단위로. **`/64` 고정이 아닙니다** (아래 설명) |
| IPv6 전제 | VPC 에 IPv6 CIDR 이 연결되어 있어야 서브넷에 IPv6 CIDR 을 붙일 수 있습니다 |
| 라우팅 | 모든 서브넷은 라우팅 테이블 하나와 연결됩니다. 만들면 자동으로 VPC 기본 라우팅 테이블에 붙습니다 |

```text
VPC      172.16.0.0/22
├─ 서브넷 172.16.0.0/24
├─ 서브넷 172.16.1.0/24
├─ 서브넷 172.16.2.0/24
└─ 서브넷 172.16.3.0/24
```

**작은 서브넷 여러 개보다 큰 서브넷을 쓰는 것이 좋습니다** (`/24` 이상 권장).
서브넷의 IP 가 부족해져도 **그 서브넷에 IP 를 추가할 수는 없습니다.** VPC 에 보조 CIDR 을
붙이고 새 서브넷을 만드는 수밖에 없습니다.

어디서 시작할지 모르겠으면 **AZ 당 퍼블릭 1개 + 프라이빗 1개**로 시작하세요. 대부분의
아키텍처는 퍼블릭보다 프라이빗 리소스가 훨씬 많으므로 **프라이빗 서브넷에 IP 를 더 많이**
할당합니다.

**IPv6 서브넷이 `/64` 고정이라고 오해하기 쉽습니다.** 문서와 예시가 거의 `/64` 를 쓰기
때문입니다. 실제로는 `/44` 부터 `/64` 까지 `/4` 단위로 고를 수 있고, `/64` 는 그중 **가장
작은 크기이면서 관례적으로 쓰는 값**입니다.

`/64` 를 고르는 실무적 이유는 개수입니다. 2.2 절에서 계산한 대로 Amazon 이 주는 `/56` VPC
안에는 `/64` 서브넷이 **256개** 들어갑니다. `/60` 으로 잡으면 16개뿐입니다.
(VPC 쪽 IPv6 크기는 3.2 절에 있습니다.)

> — 출처: [Subnet CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)

### 4.2 AWS 가 예약하는 5개 주소

서브넷 CIDR 블록의 **처음 4개와 마지막 1개** 주소는 쓸 수 없습니다.
`10.0.0.0/24` 를 예로 들면 256개 중 251개만 쓸 수 있습니다.

| 주소 | 용도 |
|---|---|
| `10.0.0.0` | 네트워크 주소 |
| `10.0.0.1` | VPC 라우터 (AWS 예약) |
| `10.0.0.2` | DNS 서버. **VPC 네트워크 범위의 기본 IP + 2**. CIDR 블록이 여러 개면 DNS 서버는 기본 CIDR 에 있고, 각 서브넷 범위의 기본값 + 2 도 모든 CIDR 블록에서 예약됩니다 |
| `10.0.0.3` | 향후 사용 (AWS 예약) |
| `10.0.0.255` | 브로드캐스트 주소. VPC 는 브로드캐스트를 지원하지 않지만 예약합니다 |

IPv6 서브넷도 같은 규칙으로 처음 4개와 마지막 1개를 예약합니다. 🆕 추가로 VPC 라우터용
링크-로컬 주소(`FE80::/10` 범위, 그리고 `FE80:ec2::1`)가 예약됩니다.

**예외** 🆕 — BYOIP(Bring Your Own IP)로 가져온 IPv4 범위는 네트워크 주소와 브로드캐스트
주소를 포함해 **범위의 모든 IP 를 쓸 수 있습니다**.

> — 출처: [Subnet CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/subnet-sizing.html)

### 4.3 퍼블릭 서브넷과 프라이빗 서브넷

둘을 가르는 것은 **라우팅 테이블 하나뿐**입니다. 서브넷 설정에 "퍼블릭" 체크박스가
있는 게 아닙니다.

| | 퍼블릭 서브넷 | 프라이빗 서브넷 |
|---|---|---|
| 인터넷 게이트웨이 경로 | 있음 | 없음 |
| 인바운드 인터넷 액세스 | 가능 | 불가 |
| 아웃바운드 인터넷 액세스 | 가능 | NAT 게이트웨이 등을 거쳐야 가능 |
| 전형적 용도 | 로드 밸런서, NAT 게이트웨이, 배스천 호스트 | 웹·앱 서버, 데이터베이스 |

**꼭 기억할 것: 서브넷은 격리 경계가 아닙니다.** AWS 문서와 교재가 함께 강조하는
지점입니다. 서브넷은 **라우팅 정책의 컨테이너**입니다. 실제 격리는 **보안 그룹**이
ENI 수준에서 수행합니다(9장).

또 하나 🆕 — VPC 에 퍼블릭 라우팅 가능한 CIDR 블록을 쓸 수도 있지만, **AWS 는 VPC CIDR
블록에서 인터넷으로의 직접 액세스를 지원하지 않습니다.** 주소가 퍼블릭이어도 게이트웨이
(인터넷 게이트웨이, 가상 프라이빗 게이트웨이, Site-to-Site VPN, Direct Connect)를 거쳐야
합니다. 그리고 AWS 는 **서브넷의 IPv4 주소 범위를 인터넷에 광고하지 않습니다.**

> — 출처: [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html)

### 4.4 서브넷 유형 세 가지

| 유형 | 만들 수 있는 리소스 |
|---|---|
| IPv4 전용 | IPv4 주소가 할당된 리소스만 |
| 듀얼 스택 | IPv4 또는 IPv6 주소가 할당된 리소스 |
| IPv6 전용 | IPv6 주소가 할당된 리소스만 |

## 5. IP 주소 관리와 IPAM

### 5.1 Amazon VPC IP Address Manager (IPAM)

계정과 VPC 가 늘어나면 스프레드시트로 IP 를 관리하기 어려워집니다. IPAM 은 이 문제를
푸는 VPC 기능입니다.

| 기능 | 내용 |
|---|---|
| **할당 자동화** | 구성 가능한 비즈니스 규칙에 따라 수백 개 계정·VPC 에 IP 주소 할당을 자동화합니다 |
| **사용량 모니터링** | IP 고갈이나 중복을 감지하고 경고합니다. 중단이 나기 전에 고칠 수 있습니다 |
| **문제 해결** | 연결 문제가 IP 구성 오류 때문인지 빠르게 판단할 수 있습니다 |
| **감사** | 모니터링 데이터를 보관해 소급 분석과 감사를 할 수 있습니다 |

개발자가 중앙 IP 관리팀의 할당을 기다리지 않아도 되므로 배포가 빨라집니다.
주소 풀이 거의 소진되면 알람을 받을 수 있고, 리소스가 풀의 할당 규칙을 어기면
알려 줍니다.

### 5.2 IPAM 풀 계층 구조

IPAM 을 만들 때 리전을 선택합니다. 생성하면 AWS 가 자동으로 **범위(scope)** 를 만듭니다.
주요 구성 요소는 **범위 / 풀(pool) / 할당(allocation)** 입니다.

```text
10.0.0.0/8                                     최상위 풀
├── 10.0.0.0/14                                리전 풀 (리전 A)
│   ├── 10.0.0.0/15  ->  VPC 10.0.0.0/16       프로덕션 풀
│   └── 10.2.0.0/15  ->  VPC 10.2.0.0/16       개발 풀
└── 10.4.0.0/14                                리전 풀 (리전 B)
    ├── 10.4.0.0/15  ->  VPC 10.4.0.0/16       프로덕션 풀
    └── 10.6.0.0/15  ->  VPC 10.6.0.0/16       개발 풀
```

먼저 최상위 풀을 만들고, 그 안에 리전 풀, 리전 풀 안에 환경별 풀을 만드는 순서입니다.
**풀의 CIDR 과 그 풀에서 VPC 에 떼어 주는 CIDR 은 다릅니다.** 위 예에서 개발 풀은
`/15` 를 갖고 있고, 그중 `/16` 하나를 VPC 에 할당했습니다. 남은 `/16` 은 다음 VPC 몫입니다.

계산해 보면 빈틈이나 겹침이 없습니다. 리전 A 의 `/14`(`10.0.0.0`\~`10.3.255.255`)가
프로덕션 `/15`(`10.0`\~`10.1`)와 개발 `/15`(`10.2`\~`10.3`)로 정확히 반씩 갈립니다.

### 5.3 IPAM 으로 연속된 탄력적 IP 받기 🆕

교재에는 없지만 실무에서 유용한 기능입니다. IPAM 을 쓰면 AWS 로부터 **연속된 퍼블릭 IPv4
주소 블록**을 받아 순차적인 탄력적 IP 주소를 리소스에 할당할 수 있습니다. 방화벽 허용
목록이나 보안 액세스 제어 목록을 관리하는 부담이 크게 줄어듭니다.

> — 출처: [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html)

**어떻게 연속이 되는가.** 일반적인 EIP 는 **리전의 AWS 공용 퍼블릭 IPv4 풀에서 임의의 주소
하나**를 받습니다. 그래서 연속될 수가 없습니다. IPAM 방식은 AWS 가 자기 소유 퍼블릭 IPv4
공간에서 **연속된 블록(`/29` \~ `/30`)을 잘라 내 사용자의 IPAM 풀에 프로비저닝**해 주고, 그
뒤로는 **IPAM 풀이 할당자**가 됩니다. 주소를 뽑는 주체가 공용 풀에서 내 풀로 바뀌는 것이
핵심입니다.

> — 출처: [Allocate sequential Elastic IP addresses from an IPAM pool](https://docs.aws.amazon.com/vpc/latest/ipam/tutorials-eip-pool.html)

## 6. 탄력적 네트워크 인터페이스와 탄력적 IP

### 6.1 탄력적 네트워크 인터페이스 (ENI)

ENI 는 VPC 안의 **가상 네트워크 카드**입니다. 인스턴스에서 떼어 다른 인스턴스에 붙일 수
있고, 그때 다음 값들을 **그대로 유지**합니다.

- 프라이빗 IP 주소
- 탄력적 IP 주소
- MAC 주소

그래서 ENI 를 옮기면 트래픽이 새 인스턴스로 따라옵니다. **라우팅 테이블이나 DNS 를
바꿀 필요가 없습니다.**

```text
[인스턴스 A]  172.31.2.15  ←── ENI (프라이빗 172.31.2.11 / 탄력적 IP 203.0.113.15)
                                    │  분리 후 재연결
[인스턴스 B]  172.31.2.18  ←────────┘
```

제약이 두 가지 있습니다.

| 제약 | 내용 |
|---|---|
| **동일 AZ** | ENI 와 인스턴스가 같은 가용 영역에 있어야 합니다. 다른 AZ 로 트래픽을 옮기는 재해 복구 시나리오에는 쓸 수 없습니다 |
| **기본 ENI** | 각 인스턴스의 기본 네트워크 인터페이스는 **분리할 수 없습니다** |

ENI 를 여러 개 쓰는 대표적인 이유입니다.

| 사용 사례 | 구성 |
|---|---|
| 관리 네트워크 분리 | `eth0` 은 퍼블릭 트래픽, `eth1` 은 더 제한적인 서브넷의 백엔드 관리 트래픽 |
| 네트워크·보안 어플라이언스 | 로드 밸런서, NAT 서버, 프록시 서버는 보통 여러 인터페이스가 필요합니다 |
| 이중 홈 인스턴스 | 프런트엔드 요청을 받고 백엔드로 별도 연결을 시작합니다 |
| 저비용 고가용성 | 장애 인스턴스에서 ENI 를 떼어 대기 인스턴스에 붙입니다 |
| 컨테이너 네트워킹 🆕 | ECS 태스크와 EKS 파드가 VPC 주소를 직접 갖도록 ENI 를 씁니다 (아래 절) |

인스턴스에 붙일 수 있는 ENI 최대 개수는 **인스턴스 유형에 따라 다릅니다.**
네트워크 카드가 여러 개인 인스턴스는 100Gbps 이상 대역폭을 제공하며, 기본 네트워크
인터페이스는 네트워크 카드 인덱스 0 에 할당되어야 합니다.

#### 컨테이너의 네트워크 인터페이스로 쓰이는 ENI 🆕

교재는 ENI 를 EC2 인스턴스 관점에서만 다룹니다. 하지만 실무에서 ENI 를 가장 많이 만들어 쓰는
쪽은 **컨테이너**입니다. 컨테이너가 VPC 주소를 직접 갖는 방식이 ENI 이기 때문입니다.

| 서비스 | ENI 를 어떻게 쓰는가 |
|---|---|
| **Amazon ECS on EC2** (`awsvpc` 모드) | 태스크마다 **자기 ENI 를 하나** 받습니다. 그 ENI 는 태스크를 호스팅하는 EC2 인스턴스에 연결됩니다 |
| **Amazon ECS on Fargate** | 기본적으로 모든 태스크가 **프라이머리 프라이빗 IP 를 가진 ENI 하나**를 받습니다. 태스크마다 ENI 가 따로 있으므로 VPC 흐름 로그 같은 기능을 태스크 단위로 쓸 수 있습니다 |
| **Amazon EKS** (Amazon VPC CNI 애드온) | 애드온이 **ENI 를 만들어 노드에 연결**하고, **파드마다 VPC 의 프라이빗 IPv4 또는 IPv6 주소**를 배정합니다 |

바로 앞의 "ENI 최대 개수는 인스턴스 유형에 따라 다르다"가 여기서 **실무 제약**으로 나타납니다.
`awsvpc` 모드는 태스크마다 ENI 가 필요하므로, **한 인스턴스에 태스크를 몇 개 올릴 수 있는지가
ENI 한도로 정해집니다.** AWS 문서의 예를 그대로 옮기면 이렇습니다.

```text
c5.large  기본 ENI 한도 3개
          − 인스턴스 기본 네트워크 인터페이스 1개
          ─────────────────────────────────────
          = awsvpc 태스크 2개
```

ENI 밀도를 높여야 하면 **`awsvpcTrunking` 계정 설정**을 켭니다. 지원하는 인스턴스 유형에서
ENI 쿼터가 늘어납니다.

한 가지 더 짚어 둘 점이 있습니다. EC2 Linux 인스턴스에서 `awsvpc` 모드 태스크를 호스팅할 때
**태스크 ENI 에는 퍼블릭 IP 가 부여되지 않습니다.** 그래서 이런 태스크가 인터넷으로 나가려면
뒤에서 볼 NAT 게이트웨이 경로(7장, 8.2 절)가 필요합니다.

> — 출처: [Task networking options for Amazon ECS tasks on Amazon EC2](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-networking-awsvpc.html)
>
> — 출처: [Amazon ECS task networking options for Fargate](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/fargate-task-networking.html)
>
> — 출처: [Assign IPs to Pods with the Amazon VPC CNI](https://docs.aws.amazon.com/eks/latest/userguide/managing-vpc-cni.html)

### 6.2 탄력적 IP 주소 (EIP)

EIP 는 **동적 클라우드 컴퓨팅을 위해 설계된 고정 퍼블릭 IPv4 주소**입니다.
계정에 할당되고, 릴리스할 때까지 내 것입니다.

| 성질 | 내용 |
|---|---|
| 고정성 | 시간이 지나도 변하지 않습니다 |
| 범위 | **특정 리전 전용**. 다른 리전으로 옮길 수 없습니다. 리전 안에서는 어떤 인스턴스·ENI 와도 재연결할 수 있습니다 |
| 쿼터 | 리전당 기본 **5개**. Service Quotas 에서 증가 요청 가능 |
| IPv6 | **지원하지 않습니다.** IPv6 주소는 기본적으로 고정이므로 EIP 가 필요 없습니다 |
| 출처 | Amazon IPv4 풀 또는 BYOIP 풀. **BYOIP 풀에서 할당한 EIP 는 쿼터에 포함되지 않습니다** |

EIP 를 인스턴스에 연결하면 기존 퍼블릭 IPv4 주소는 Amazon 풀로 반환됩니다.
**그 주소는 다시 쓸 수 없고, EIP 로 변환할 수도 없습니다.**

AWS 권장 사용법은 명확합니다. **EIP 는 장애 시 주소를 다른 인스턴스로 재매핑하는 용도로
쓰고, 그 밖의 노드 간 통신에는 DNS 호스트 이름을 씁니다.**

```text
장애 전:  EIP 203.0.113.15 ──→ 인스턴스 (172.31.0.50)  ✗ 장애
장애 후:  EIP 203.0.113.15 ──→ 인스턴스 (172.31.0.51)  ✓ 정상
```

### 6.3 EIP 요금 🔄

**교재의 강사 노트는 "인스턴스가 실행되는 동안에는 인스턴스와 연결된 하나의 탄력적 IP
주소에 대해 요금이 부과되지 않습니다"라고 적었습니다. 이는 현재와 다릅니다.**

현행 문서는 이렇게 서술합니다.

- **사용 중이든 유휴 상태든 모든 탄력적 IP 주소에 요금이 부과됩니다.**
- AWS 는 **실행 중인 인스턴스에 연결된 퍼블릭 IPv4 주소와 탄력적 IP 주소를 포함해
  모든 퍼블릭 IPv4 주소에 요금을 부과합니다.**

교재 자체도 앞뒤가 맞지 않습니다. 슬라이드 8 의 강사 노트에는 "2024년 2월 1일부터 모든
퍼블릭 IPv4 주소에 대해 과금된다"고 적혀 있는데, 슬라이드 28 에는 위의 옛 규칙이 남아
있습니다. **슬라이드 8 쪽이 맞습니다.**

실무 함의는 단순합니다. **쓰지 않는 EIP 와 퍼블릭 IPv4 주소는 비용입니다.**
프라이빗 서브넷 + NAT 게이트웨이 구성이나 IPv6 전환이 비용 관점에서도 의미를 갖습니다.
구체적인 단가는 바뀌므로 요금 페이지에서 확인하세요.

> — 출처: [Elastic IP addresses](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/elastic-ip-addresses-eip.html)

### 6.4 교재에 없는 EIP 기능 🆕

| 기능 | 내용 |
|---|---|
| **계정 간 전송** | 탄력적 IP 주소를 다른 AWS 계정으로 전송할 수 있습니다 |
| **네트워크 경계 그룹** | EIP 할당 시 네트워크 경계 그룹을 지정해 CIDR 블록을 광고하는 위치를 제한할 수 있습니다. 지정하지 않으면 리전의 모든 AZ 를 포함하는 그룹이 설정됩니다 |

> — 출처: [Elastic IP addresses](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/elastic-ip-addresses-eip.html)

## 7. 라우팅 테이블

### 7.1 라우팅 테이블의 규칙

라우팅 테이블은 **트래픽을 어디로 보낼지 정하는 규칙 집합**입니다.

- 각 VPC 에는 **주(기본) 라우팅 테이블**이 하나 있습니다
- **모든 서브넷은 라우팅 테이블 하나와 연결되어야** 합니다
- VPC 에 할당된 CIDR 은 자동으로 **로컬 경로**에 추가됩니다
- 각 경로는 **대상 위치**(IP 범위)와 **대상**(게이트웨이·ENI·연결)을 지정합니다
- 사용자 지정 라우팅 테이블은 **연결이 없을 때만** 삭제할 수 있습니다

| 대상 위치 | 대상 | 의미 |
|---|---|---|
| `172.31.0.0/16` | `local` | VPC 내부 통신 |
| `0.0.0.0/0` | `igw-...` | 그 밖의 모든 IPv4 트래픽을 인터넷 게이트웨이로 |

**모범 사례**: 기본 라우팅 테이블은 원래 상태로 두고, 서브넷마다 사용자 지정 라우팅
테이블을 만들어 **명시적으로 연결**합니다. 그러면 각 서브넷의 라우팅을 의도적으로
통제할 수 있습니다.

### 7.2 가장 긴 접두사 일치

경로가 여럿 일치하면 **가장 구체적인 경로**가 이깁니다. 이를 **가장 긴 접두사
일치(longest prefix match)** 라고 합니다.

```text
라우팅 테이블
  10.0.0.0/16   → local
  10.0.5.0/24   → pcx-abc123      ← 10.0.5.7 로 가는 트래픽은 이 경로를 씁니다
  0.0.0.0/0     → igw-abc123
```

### 7.3 IPv4 와 IPv6 는 완전히 별개입니다

**`0.0.0.0/0` 경로에 IPv6 주소가 자동으로 포함되지 않습니다.** IPv6 기본 경로는
`::/0` 로 따로 만들어야 합니다. 실습에서 자주 놓치는 부분입니다.

프라이빗 듀얼 스택 서브넷의 전형적인 라우팅 테이블입니다.

| 대상 위치 | 대상 | 역할 |
|---|---|---|
| `10.0.0.0/16` | `local` | VPC 내부 IPv4 |
| `2001:db8:1234:1a00::/56` | `local` | VPC 내부 IPv6 |
| `0.0.0.0/0` | `nat-...` (NAT 게이트웨이) | IPv4 아웃바운드만 허용, 인바운드 차단 |
| `::/0` | `eigw-...` (송신 전용 인터넷 게이트웨이) | IPv6 아웃바운드만 허용, 인바운드 차단 |

> Amazon 이 제공하는 IPv6 CIDR 블록은 글로벌 유니캐스트라 "이미 퍼블릭"이지만,
> **라우팅 테이블에 경로가 없으면 실제로 인터넷에 존재하지 않습니다.**
> 주소가 퍼블릭인 것과 도달 가능한 것은 다릅니다.
> (IPAM 으로 프라이빗 IPv6 를 쓰는 경우는 애초에 광고되지 않습니다. 2.3 절 참조)

### 7.4 동적 라우팅: Amazon VPC Route Server 🆕

> 출시: **2025년 3월 31일** (문서 이력 기준). 교재 콘텐츠 시점보다 뒤입니다.

지금까지 본 라우팅 테이블은 모두 **정적 경로**입니다. 사람이 경로를 넣고, 대상이 죽어도
경로는 그대로 남습니다. 교재는 여기까지만 다룹니다.

이게 실제로 문제가 되는 대표적인 상황이 **보안 어플라이언스**입니다. 방화벽이나 IDS/IPS 를
EC2 인스턴스로 직접 운영하면, 트래픽을 그 어플라이언스로 보내려고 **라우팅 테이블에
어플라이언스의 ENI 를 대상으로 하는 정적 경로**를 넣습니다. 그런데 그 어플라이언스가 죽으면
**경로는 죽은 ENI 를 계속 가리킵니다.** 사람이 알아채고 라우팅 테이블을 직접 고쳐야
트래픽이 다시 흐릅니다. **VPC Route Server 가 이 부분을 보완합니다.**

**Amazon VPC Route Server** 는 VPC 안에서 **BGP 로 동적 라우팅**을 합니다. 워크로드와
BGP 세션을 맺고, **선호하는 IPv4 또는 IPv6 경로로 라우팅 테이블을 자동 갱신**해
라우팅 내결함성을 확보합니다. 서드 파티 워크로드(방화벽, 라우터 어플라이언스 등)와의
상호 운용성을 높이려고 만든 기능입니다.

**어떻게 동작하는가**

용어가 일곱 개나 나오지만, 하는 일은 **네 단계**뿐입니다. 순서대로 따라가면 됩니다.

```text
[1] 디바이스가 "이 대역은 나한테 보내" 라고 알립니다  (BGP)

        Device A   eni-abcd   192.0.0.0/24   MED 0     <== 더 선호
        Device B   eni-efgh   192.0.0.0/24   MED 큼
            |
            v

[2] route server 가 받은 경로 중에서 최적을 고릅니다

        받은 경로 전부  ->  RIB
        고른 경로       ->  FIB
            |
            v

[3] FIB 의 경로를 라우팅 테이블에 써 넣습니다

        route table :   192.0.0.0/24  ->  eni-abcd
            |
            v

[4] 서브넷의 트래픽이 그 경로를 따라 Device A 로 갑니다
```

정리하면 **"디바이스가 알린다 → 라우트 서버가 고른다 → 라우팅 테이블에 써 넣는다"** 입니다.
앞에서 본 정적 경로에서는 [3]을 사람이 했습니다.

나머지 용어는 위 네 단계의 **어느 자리에 붙는 이름인지**만 알면 됩니다.

| 용어 | 그림에서 어디 | 무엇인가 |
|---|---|---|
| **peer** | [1] 의 BGP 세션 | 엔드포인트와 디바이스 사이의 **세션**입니다 |
| **endpoint** | [1] 의 세션이 맺히는 자리 | **서브넷 안에 있는 AWS 관리 구성 요소**입니다. BGP 연결을 돕습니다 |
| **route server** | [2] 전체 | RIB 와 FIB 를 하나씩 가지고 최적 경로를 고릅니다 |
| **RIB** | [2] 의 "받은 경로 전부" | BGP 피어에서 배운 모든 경로와 토폴로지를 담는 데이터베이스입니다 |
| **FIB** | [2] 의 "고른 경로" | RIB 를 평가해 고른 최적 경로입니다. **라우팅 테이블에 실제로 설치되는 것이 이쪽**입니다. RIB 가 바뀌면 다시 계산됩니다 |
| **propagation** | [3] 을 켜는 스위치 | 켜면 FIB 의 경로를 지정한 라우팅 테이블에 설치합니다. IPv4·IPv6 모두 지원합니다 |
| **association** | 그림 밖 (사전 준비) | 라우트 서버를 VPC 에 붙이는 연결입니다 |

**peer 로 붙일 수 있는 디바이스의 조건**은 세 가지입니다. VPC 안에 탄력적 네트워크
인터페이스가 있어야 하고, BGP 를 지원해야 하고, **BGP 세션을 먼저 시작할 수 있어야** 합니다.
EC2 인스턴스로 운영하는 방화벽이나 네트워크 보안 기능이 대표적인 대상입니다(6.1 절 ENI).

**장애가 나면 어떻게 되는가**

위 그림에서 Device A 와 B 가 둘 다 BGP 로 "`192.0.0.0/24` 로 가는 트래픽을 내가 받겠다"고
알립니다. A 의 MED 값이 더 작으므로 라우트 서버는 **A 를 선호**합니다.

바뀌는 것은 라우팅 테이블의 **한 줄**입니다.

```text
[ 정상 ]
    route table :  192.0.0.0/24  ->  eni-abcd      Device A

[ Device A 다운 ]
    route table :  192.0.0.0/24  ->  eni-efgh      Device B
                                     ^^^^^^^^
                                     이 한 줄이 자동으로 바뀝니다
```

그 사이에 일어나는 일은 여섯 단계입니다.

1. Device A 가 죽습니다.
2. **endpoint 가 peer 에 설정된 BFD** 로 장애를 감지합니다.
3. endpoint 가 라우트 서버에 알려, **죽은 디바이스를 넥스트 홉으로 삼던 경로를 RIB 에서
   회수**합니다.
4. 라우트 서버가 RIB 에서 **FIB 를 다시 계산**해 남은 최적 경로를 고릅니다.
5. 라우트 서버가 **라우팅 테이블을 갱신**합니다.
6. 새 트래픽이 대기 디바이스로 흐릅니다.

지원하는 라우팅 테이블 유형:

| 유형 | 지원 |
|---|---|
| 서브넷에 연결되지 않은 VPC 라우팅 테이블 | 지원 |
| 서브넷 라우팅 테이블 | 지원 |
| 인터넷 게이트웨이 라우팅 테이블 | 지원 |
| **가상 프라이빗 게이트웨이에 연결된 라우팅 테이블** | **미지원** |

Transit Gateway 라우팅 테이블에 경로를 전파하려면 Route Server 가 아니라
**Transit Gateway Connect** 를 씁니다.

구성 순서는 공식 튜토리얼이 정해 두었습니다. **propagation 을 켜는 것이 peer 를 만드는
것보다 먼저**라는 점만 기억하면 됩니다.

```text
1. IAM 역할 권한 구성
2. 라우트 서버 생성
3. 라우트 서버를 VPC 에 association
4. 라우트 서버 endpoint 생성
5. 라우트 서버 propagation 활성화     <-- peer 보다 먼저입니다
6. 라우트 서버 peer 생성
7. 디바이스에서 BGP 세션 시작
```

두 번째 단계의 명령입니다. `--amazon-side-asn` 은 **필수**이고, BGP 세션의 AWS 측 ASN 을
지정합니다. 값은 1\~4294967295 이지만 프라이빗 ASN 범위(16비트는 64512\~65534,
32비트는 4200000000\~4294967294)를 쓰라고 권장합니다.

```bash
# 라우트 서버 생성 (예시 65000 은 권장 프라이빗 ASN 범위 안입니다)
aws ec2 create-route-server --amazon-side-asn 65000
```

BGP 세션을 시작하는 쪽은 **AWS 가 아니라 디바이스**입니다(7단계). 앞서 본 "디바이스가 BGP
세션을 먼저 시작할 수 있어야 한다"는 조건이 여기서 확인됩니다.

> — 출처: [Dynamic routing in your VPC using VPC Route Server](https://docs.aws.amazon.com/vpc/latest/userguide/dynamic-routing-route-server.html)

## 8. 인터넷·NAT·송신 전용 게이트웨이

### 8.1 인터넷 게이트웨이

| 성질 | 내용 |
|---|---|
| 가용성 | 가상이고, 수평적으로 확장되며, 중복되고, 가용성이 뛰어납니다 |
| 대역폭 | **제약이 없습니다.** 단일 장애 지점이 아닙니다 |
| 프로토콜 | **IPv4 와 IPv6 모두** 지원 |

역할이 두 가지입니다.

1. 인터넷 라우팅이 가능한 트래픽에 대한 **라우팅 테이블의 대상**을 제공합니다
2. 퍼블릭 IP 와 프라이빗 IP 를 매핑하는 **NAT 를 수행**합니다

```text
아웃바운드:  인스턴스(172.31.2.15) → 인터넷 게이트웨이가 소스를 203.0.113.15 로 변환 → 인터넷
인바운드:    인터넷 → 203.0.113.15 수신 → 인터넷 게이트웨이가 172.31.2.15 로 변환 → 인스턴스
```

**서브넷은 기본적으로 아웃바운드 트래픽을 허용하지 않습니다.** 라우팅 테이블에
인터넷 게이트웨이를 대상으로 하는 경로를 만들어야 나갈 수 있습니다.

### 8.2 NAT 게이트웨이

프라이빗 서브넷의 인스턴스가 **밖으로는 나가되 밖에서 들어오지는 못하게** 하는
관리형 서비스입니다.

| 성질 | 값 |
|---|---|
| 프로토콜 | **IPv4 전용**. 지원 프로토콜은 TCP, UDP, ICMP 🆕 |
| 대역폭 | **5Gbps → 자동으로 100Gbps 까지** 확장 |
| 패킷 처리량 🆕 | **초당 100만 패킷 → 자동으로 초당 1,000만 패킷까지** 확장. 넘으면 패킷을 버립니다 |
| 동시 연결 🆕 | IPv4 주소당 고유 대상별 **최대 55,000개**. 고유 대상은 (대상 IP, 대상 포트, 프로토콜) 조합입니다. IPv4 주소를 최대 8개(기본 1 + 보조 7)까지 연결해 늘릴 수 있습니다 |
| 가용성 | **특정 가용 영역에 생성되고 그 영역 안에서만 중복성**을 갖습니다 |
| 보안 그룹 | **연결할 수 없습니다.** 인스턴스의 보안 그룹으로 제어합니다 |
| 포트 🆕 | 1024–65535 를 사용합니다. 네트워크 ACL 을 쓸 때 고려해야 합니다 |
| MTU 🆕 | 8500 바이트를 지원합니다 |

```text
프라이빗 서브넷                    퍼블릭 서브넷
인스턴스 172.31.32.75  ──→  NAT 게이트웨이 (EIP 203.0.113.15)  ──→  인터넷 게이트웨이  ──→  인터넷
                            소스 IP 를 203.0.113.15 로 변환
```

**가용 영역 함정**: NAT 게이트웨이의 고가용성은 **자기 AZ 안으로 제한됩니다.**
여러 AZ 의 리소스가 하나의 NAT 게이트웨이를 공유하면 그 AZ 가 내려갈 때 **다른 AZ 의
리소스도 인터넷 액세스를 잃습니다.** 그래서 전통적인 모범 사례는 **AZ 마다 NAT 게이트웨이를
만들고, 같은 AZ 의 NAT 게이트웨이를 쓰도록 라우팅을 구성**하는 것입니다.

기타 특성:
- **NAT64** 를 지원합니다. Route 53 Resolver 의 DNS64 와 함께 쓰면 IPv6 워크로드가
  IPv4 리소스와 통신할 수 있습니다
- **프라이빗 NAT 게이트웨이**를 쓰면 CIDR 범위가 겹치는 네트워크 간 통신도 가능합니다
- 🆕 VPC 피어링을 **통해서** NAT 게이트웨이로 트래픽을 라우팅할 수는 없습니다.
  (`클라이언트 → 피어링 → NAT → 인터넷` 은 불가, `클라이언트 → NAT → 피어링 → 대상` 은 가능)

> — 출처: [NAT gateway basics](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html)

### 8.3 리전 NAT 게이트웨이 🆕

> 출시: **2025년 11월 19일** (문서 이력 기준). 이 문서에서 다루는 항목 중 가장 최근입니다.

교재에 없는 기능이고, 위의 "AZ 마다 NAT 게이트웨이" 문제를 정면으로 해결합니다.
**리전 NAT 게이트웨이**는 워크로드가 있는 곳을 따라 **가용 영역 전체로 자동 확장·축소**
됩니다.

| | 영역(zonal) NAT 게이트웨이 | 리전(regional) NAT 게이트웨이 |
|---|---|---|
| 배치 | AZ 마다 만들고 퍼블릭 서브넷에 둡니다 | **퍼블릭 서브넷이 필요 없습니다.** VPC 만 지정합니다 |
| 라우팅 | AZ 마다 별도 경로를 구성합니다 | **단일 NAT ID** 를 모든 AZ 에서 씁니다 |
| AZ 확장 시 | NAT 를 만들고 라우팅 테이블을 고쳐야 합니다 | 자동으로 확장·축소됩니다 |
| AZ 당 IP 주소 | 8개 | **32개** |
| 프라이빗 NAT | 지원 | **지원하지 않습니다** |

- IP 주소마다 고유 대상에 대한 동시 연결 한도가 **55,000 증가**합니다
- 새 AZ 에 리소스가 생긴 뒤 확장되는 데 **최대 60분**이 걸릴 수 있습니다.
  그 사이 트래픽은 기존 AZ 의 NAT 게이트웨이가 교차 영역으로 처리합니다
- **자동 모드**(AWS 가 IP 와 AZ 확장을 관리, 권장)와 **수동 모드**가 있습니다
- 리전 NAT 게이트웨이를 만들면 AWS 가 인터넷 게이트웨이 경로가 미리 구성된 라우팅
  테이블을 자동으로 만들어 줍니다

```bash
# 리전 NAT 게이트웨이 생성
aws ec2 create-nat-gateway --vpc-id vpc-12345678 --availability-mode regional
```

**프라이빗 연결이 필요한 경우를 제외하면** 리전 모드를 고려하라는 것이 문서의 안내입니다.

> — 출처: [Regional NAT gateways for automatic multi-AZ expansion](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateways-regional.html)

### 8.4 송신 전용 인터넷 게이트웨이

IPv6 판 "나가기만 허용"입니다. IPv6 에는 주소 절약용 NAT 가 없기 때문에 별도 게이트웨이가
있습니다.

| 성질 | 내용 |
|---|---|
| 프로토콜 | **IPv6 전용** |
| 상태 추적 | **스테이트풀**입니다. 그래서 나간 요청의 응답은 돌아올 수 있습니다 |
| 가용성 | 가상, 수평 확장, 중복, 고가용성 |
| 보안 그룹 | **연결할 수 없습니다.** 인스턴스의 보안 그룹과 네트워크 ACL 로 제어합니다 |

라우팅 테이블에 `::/0` 또는 특정 IPv6 범위를 이 게이트웨이로 보내는 경로를 추가합니다.

**주의할 점이 하나 있습니다.** 이 게이트웨이는 **퍼블릭 IPv6 주소**의 아웃바운드를 허용하는
장치입니다. IPAM 으로 받은 **프라이빗 IPv6**(ULA 또는 프라이빗 GUA)는 이 게이트웨이를
경로에 넣어도 인터넷으로 나가지 못하고 인터넷 게이트웨이 경계에서 폐기됩니다(2.3 절).

### 8.5 게이트웨이 세 개 비교

| | 인터넷 게이트웨이 | NAT 게이트웨이 | 송신 전용 인터넷 게이트웨이 |
|---|---|---|---|
| 프로토콜 | IPv4 + IPv6 | IPv4 전용 | IPv6 전용 |
| 방향 | 양방향 | 아웃바운드만 | 아웃바운드만 |
| 상태 추적 | — | 스테이트풀 | 스테이트풀 |
| 범위 | VPC | 영역 또는 리전 | VPC |
| 보안 그룹 | 연결 불가 | 연결 불가 | 연결 불가 |

요금 체계는 게이트웨이마다 다르고 바뀌므로 이 표에 넣지 않았습니다.
[Amazon VPC 요금](https://aws.amazon.com/vpc/pricing/) 페이지에서 확인하세요.

## 9. 트래픽 필터링

> 교재는 이 주제를 **"VPC 의 기본 트래픽 필터링 메커니즘"** 이라고 부릅니다. 이 문서는
> 교재 범위(보안 그룹, 네트워크 ACL)에 9.4·9.5 절을 더했기 때문에 **"기본"** 을 뗀
> 제목을 씁니다. 대조할 때 참고하세요.

### 9.1 보안 그룹과 네트워크 ACL

VPC 에는 방화벽이 두 계층 있습니다. 시험과 실무 양쪽에서 헷갈리는 지점이라 표로
정리합니다.

| | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 적용 경계 | **ENI(인스턴스) 수준** | **서브넷 수준** |
| 상태 추적 | **스테이트풀** — 허용된 요청의 응답은 자동 허용 | **스테이트리스** — 인바운드·아웃바운드 규칙을 각각 명시해야 함 |
| 규칙 | **허용(allow)만** 가능 | 허용과 **거부(deny)** 모두 가능 |
| 기본값 | 기본 SG: 모든 아웃바운드 허용 / 사용자 지정 SG: **인바운드 규칙 없음**, 아웃바운드 허용 | 기본 네트워크 ACL: 모든 인바운드·아웃바운드 허용 |
| 소스 지정 | IP, CIDR, **다른 보안 그룹 참조 가능** | IP, CIDR 만 |
| 요금 | 없음 | 없음 |
| 실무 위치 | **기본 필터링 수단** | **보조 가드레일** |

보안 그룹에 아웃바운드 규칙이 하나도 없으면 아웃바운드 트래픽이 **허용되지 않습니다.**

AWS 고객이 보안 그룹을 주로 쓰는 이유는 스테이트풀이고 **다른 보안 그룹을 참조하는
규칙**을 쓸 수 있어서입니다. 네트워크 ACL 은 특정 트래픽 하위 집합을 거부하거나
서브넷 전체 가드레일을 세울 때 효율적입니다.

### 9.2 보안 그룹 연결로 3티어 구성하기

보안 그룹이 다른 보안 그룹을 소스로 참조하면 IP 를 하드코딩하지 않고 티어를 잠글 수
있습니다. **트래픽이 상위 티어에서 하위 티어로만 흐르게** 됩니다.

```text
인터넷 ──443──→ [웹 SG]  ──80──→ [앱 SG]  ──3306──→ [데이터 SG]
```

| 티어 | 인바운드 규칙 | 소스 |
|---|---|---|
| 웹 | HTTPS 443 허용 | `0.0.0.0/0` (또는 로드 밸런서) |
| 앱 | HTTP 80 허용 | **웹 SG** |
| 데이터 | TCP 3306 허용 | **앱 SG** |

세 티어 모두 SSH 22 관리 액세스는 **회사 네트워크에서만** 허용합니다.

이 구성의 가치는 명확합니다. 한 티어가 침해되어도 **서브넷 전체 액세스가 자동으로
열리지 않습니다.**

### 9.3 프라이빗 인스턴스의 아웃바운드 경로

프라이빗 서브넷 인스턴스가 소프트웨어 업데이트를 받거나 외부 API 를 호출하는 경로를
따라가 보면 **서브넷 경계를 두 번** 넘습니다.

```text
[프라이빗 서브넷]                     [퍼블릭 서브넷]
인스턴스
  │ 라우팅 테이블: 0.0.0.0/0 → NAT 게이트웨이
  │ 네트워크 ACL #1 통과
  ↓
NAT 게이트웨이 (소스 IP 를 자기 것으로 변환)
  │ 라우팅 테이블: 0.0.0.0/0 → 인터넷 게이트웨이
  │ 네트워크 ACL #2 통과
  ↓
인터넷 게이트웨이 (NAT 게이트웨이의 프라이빗 IP → EIP 로 변환)
  ↓
인터넷
```

**네트워크 ACL 세트 2개와 라우팅 테이블 2개를 통과합니다.** 네트워크 ACL 은
스테이트리스이므로 **양쪽 서브넷 모두에서 임시 포트의 반환 트래픽을 명시적으로
허용**해야 합니다. 이걸 빼먹으면 "나가기는 하는데 응답이 안 온다"가 됩니다.

### 9.4 VPC Block Public Access 🆕

> 출시: **2024년 11월 19일** (문서 이력 기준). 교재 콘텐츠 시점보다 뒤입니다.

교재에 없는 계정 수준 안전장치입니다. 실수로 퍼블릭 경로가 열리는 것을 막습니다.

**VPC Block Public Access(BPA)** 는 AWS 계정 전체에서 VPC 리소스에 대한 퍼블릭 인터넷
액세스를 중앙에서 차단하는 보안 기능입니다.

| 모드 | 차단 범위 |
|---|---|
| **Bidirectional** | 해당 리전의 인터넷 게이트웨이·송신 전용 인터넷 게이트웨이를 지나는 **모든** 트래픽을 차단 |
| **Ingress-only** | 인바운드만 차단. NAT 게이트웨이와 송신 전용 인터넷 게이트웨이의 아웃바운드는 허용 |

차단하고 싶지 않은 트래픽에는 VPC 또는 서브넷 단위로 **예외(exclusion)** 를 만듭니다.
예외 모드는 `Bidirectional`(양방향 허용)과 `Egress-only`(아웃바운드만 허용)입니다.

앞에서 배운 것과 연결하면 이렇게 정리됩니다. 라우팅 테이블은 "경로를 만드는" 도구이고,
보안 그룹과 네트워크 ACL 은 "패킷을 거르는" 도구이고, VPC BPA 는 **"계정 전체에서
퍼블릭 경로 자체를 금지하는"** 도구입니다.

> — 출처: [Block public access to VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/security-vpc-bpa.html)

### 9.5 계층을 하나 더: AWS Network Firewall 🆕

> **먼저 짚을 것**: AWS Network Firewall 은 **2020년 11월 16일에 첫 릴리스**되었습니다
> (문서 이력 기준). 교재보다 한참 앞섭니다. 이 과정이 **네트워크 보안을 범위 밖으로
> 두었기 때문에** 교재에 없는 것입니다.

교재 범위는 아니지만 **보안 그룹과 네트워크 ACL 로 부족한 지점이 어디인지**는 알아 둘
가치가 있습니다.

둘은 **IP·포트·프로토콜** 수준에서 판단합니다. "이 포트를 이 대역에 열어라"는 표현은 되지만,
"이 도메인만 허용하라"거나 "패킷 내용을 검사하라"는 표현은 안 됩니다.

**AWS Network Firewall** 은 VPC 경계에 두는 **스테이트풀 관리형 네트워크 방화벽 겸
침입 탐지·방지(IDS/IPS) 서비스**입니다. 오픈 소스 IPS 인 **Suricata** 를 쓰고
Suricata 호환 규칙을 지원합니다.

| 할 수 있는 것 | 예 |
|---|---|
| 알려진 AWS 서비스 도메인·IP 엔드포인트만 통과 | Amazon S3 로 가는 트래픽만 허용 |
| 알려진 악성 도메인 목록으로 접근 제한 | 애플리케이션이 접근할 도메인 이름을 제한 |
| **심층 패킷 검사** | VPC 로 들어오고 나가는 트래픽의 내용을 검사 |
| **스테이트풀 프로토콜 감지** | 포트와 무관하게 HTTPS 같은 프로토콜을 식별해 필터링 |

필터링 지점은 **인터넷 게이트웨이, NAT 게이트웨이, VPN, Direct Connect** 를 오가는
트래픽입니다.

기본 동작은 **소스 보존 모드(source-preservation mode)** 입니다. VPC 엔드포인트에서
트래픽을 받아 스테이트풀 규칙 엔진으로 검사한 뒤 원래 출발지·목적지 IP 를 그대로 유지한
채 돌려보냅니다. TCP, UDP, ICMP 를 모두 지원합니다.

여러 계정에 걸쳐 방화벽을 중앙에서 관리하려면 **AWS Firewall Manager** 를 씁니다.

> — 출처: [What is AWS Network Firewall?](https://docs.aws.amazon.com/network-firewall/latest/developerguide/what-is-aws-network-firewall.html)

**어떤 시그니처를 탐지하는가**

Suricata 호환 규칙을 직접 쓸 수도 있지만, AWS 가 관리하는 **위협 시그니처 규칙 그룹**을
가져다 쓰는 방법이 있습니다. 탐지 범주는 멀웨어와 취약점 공격, 서비스 거부 시도, 봇넷,
웹 공격, 자격 증명 피싱, 스캐닝 도구, 메일·메시징 공격입니다. 침입 탐지용 시그니처와
공정 사용 정책 적용, 신종 위협 대비 시그니처도 있습니다. 현재는 **Suricata 호환 스테이트풀
관리형 규칙 그룹만** 지원합니다.

규칙 그룹 이름 뒤에는 `StrictOrder` 또는 `ActionOrder` 가 붙습니다. 방화벽 정책의 **규칙
평가 순서**와 맞는 것만 정책에 추가할 수 있습니다.

> — 출처: [AWS threat signature managed rule groups for AWS Network Firewall](https://docs.aws.amazon.com/network-firewall/latest/developerguide/aws-managed-rule-groups-threat-signature.html)

**아키텍처**

구조를 이해하는 데 중요한 개념 두 개가 있습니다.

- **방화벽 서브넷** — Network Firewall 전용으로 지정하는 서브넷입니다. 방화벽 엔드포인트는
  **자기가 있는 서브넷의 트래픽은 필터링할 수 없으므로**, 이 서브넷에는 다른 것을 두지
  않습니다
- **라우팅 테이블로 트래픽을 유도** — 8장에서 배운 것과 같은 방식입니다. 방화벽이
  트래픽을 "가로채는" 게 아니라, 라우팅 테이블이 방화벽 엔드포인트를 가리키게 만듭니다

트래픽이 지나는 순서는 이렇습니다. AWS 문서의 단일 AZ 예시 값을 그대로 썼습니다.

```text
        인터넷
          ^
          |
     +---------+
     |   IGW   |            igw-1232
     +---------+
          ^
          |                 VPC 10.0.0.0/16
          v
     +-------------------+
     | firewall subnet   |  방화벽 전용 서브넷
     |     endpoint      |  vpce-4114
     +-------------------+
          ^
          |
          v
     +-------------------+
     | customer subnet   |  10.0.2.0/24  (EC2 등 워크로드)
     +-------------------+
```

핵심은 **라우팅 테이블이 세 개**가 되고, 고객 서브넷의 기본 경로가 인터넷 게이트웨이에서
방화벽 엔드포인트로 바뀐다는 점입니다.

```text
[ 방화벽 넣기 전 ]  라우팅 테이블 2개

  customer subnet RT :  10.0.0.0/16  ->  local
                        0.0.0.0/0    ->  igw-1232


[ 방화벽 넣은 후 ]  라우팅 테이블 3개

  internet gateway RT :  10.0.2.0/24  ->  vpce-4114      들어오는 트래픽을 방화벽으로
  firewall subnet RT  :  10.0.0.0/16  ->  local
                         0.0.0.0/0    ->  igw-1232       검사 끝난 트래픽을 인터넷으로
  customer subnet RT  :  10.0.0.0/16  ->  local
                         0.0.0.0/0    ->  vpce-4114      나가는 트래픽을 방화벽으로
                                          ^^^^^^^^^
                                          전에는 igw-1232 였습니다
```

인터넷 게이트웨이 라우팅 테이블이 등장하는 것이 눈에 걸릴 수 있습니다. 7.4 절에서 본
**인터넷 게이트웨이 라우팅 테이블**이 바로 이런 용도입니다. 들어오는 트래픽도 방화벽을
거치게 하려면 게이트웨이 쪽에서도 방향을 잡아 줘야 합니다.

> — 출처: [Simple single zone architecture with an internet gateway using AWS Network Firewall](https://docs.aws.amazon.com/network-firewall/latest/developerguide/arch-single-zone-igw.html)

> 세 계층을 한 줄로 정리하면 이렇습니다. **보안 그룹**은 ENI 경계에서 IP·포트를,
> **네트워크 ACL** 은 서브넷 경계에서 IP·포트를, **Network Firewall** 은 VPC 경계에서
> 도메인과 패킷 내용까지 봅니다. 세 개는 대체 관계가 아니라 계층입니다.

## 10. 한눈에 정리

### 계층으로 보는 VPC

| 계층 | 리소스 | 범위 |
|---|---|---|
| 리전 | VPC, 인터넷 게이트웨이, 라우팅 테이블 | 리전 |
| 가용 영역 | 서브넷, 영역 NAT 게이트웨이 | 단일 AZ |
| 인터페이스 | ENI, 보안 그룹, 탄력적 IP | ENI |

### 자주 틀리는 것

| 오해 | 사실 |
|---|---|
| 서브넷이 격리 경계다 | 격리는 보안 그룹이 한다. 서브넷은 라우팅 정책의 컨테이너 |
| `0.0.0.0/0` 이면 IPv6 도 포함된다 | 아니다. `::/0` 을 따로 만들어야 한다 |
| VPC CIDR 을 나중에 넓힐 수 있다 | 못 한다. 보조 CIDR 을 추가할 수만 있다 |
| 서브넷 `/24` 는 256개 다 쓸 수 있다 | 5개는 AWS 예약. 251개다 |
| NAT 게이트웨이 하나로 다중 AZ 고가용성이 된다 | 영역 모드는 자기 AZ 안에서만. AZ 마다 만들거나 리전 모드를 쓴다 |
| 실행 인스턴스에 붙은 EIP 1개는 무료다 | 지금은 모든 퍼블릭 IPv4 에 과금된다 |
| IPv6 전용 VPC 를 만들 수 있다 | 못 한다. VPC 는 IPv4 CIDR 이 필수. 단 IPv6 전용 서브넷은 가능 |

### 쿼터 요약

| 항목 | 기본값 | 조정 |
|---|---|---|
| 리전당 VPC | 5 | 가능 |
| VPC당 서브넷 | 200 | 가능 |
| VPC당 IPv4 CIDR 블록 | 5 | 최대 50 |
| VPC당 IPv6 CIDR 블록 | 5 | — |
| VPC당 라우팅 테이블 | 200 | 가능 |
| VPC당 네트워크 ACL | 200 | 가능 |

## 11. 교재 대비 변경 사항

교재를 함께 보는 분들을 위해, 이 문서가 교재와 다르게 적은 부분과 그 근거를 모았습니다.

### 11.1 교재 기술이 사실과 다른 항목

| 교재 기재 (위치) | 확인된 내용 | 근거 |
|---|---|---|
| `172.16.0.0/12` 범위를 `172.16.0.0~172.16.31.255` 로 기재 (슬라이드 10 강사 노트) | 실제 범위는 `172.16.0.0 ~ 172.31.255.255` 입니다 | [VPC CIDR blocks](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-cidr-blocks.html) |
| "인스턴스가 실행되는 동안에는 인스턴스와 연결된 하나의 탄력적 IP 주소에 대해 요금이 부과되지 않습니다" (슬라이드 28 강사 노트) | 사용 중이든 유휴 상태든 **모든** 탄력적 IP 주소에 요금이 부과됩니다. AWS 는 실행 중인 인스턴스에 연결된 퍼블릭 IPv4 주소를 포함해 모든 퍼블릭 IPv4 주소에 과금합니다 | [Elastic IP addresses](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/elastic-ip-addresses-eip.html) |
| "IPv6 에는 IPv4 와 같이 프라이빗 주소 범위가 할당되지 않는다", "IPv6 주소에는 전통적인 의미의 프라이빗 주소를 위한 범위가 지정되어 있지 않다" (슬라이드 10 강사 노트) | **고유 로컬 주소(ULA)가 IPv6 의 프라이빗 주소 공간입니다.** 같은 슬라이드의 표에도 `fc00::/7` 이 프라이빗 공간으로 적혀 있어 교재 안에서 서로 어긋납니다. AWS 문서는 퍼블릭·프라이빗 IPv6 를 모두 지원한다고 명시하며, 프라이빗 IPv6 는 ULA 와 (옵트인) 프라이빗 GUA 두 종류로 IPAM 을 통해 씁니다 (2.3 절) | [IP addressing for your VPCs and subnets](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-ip-addressing.html) |

교재 **슬라이드 32 의 표**는 프라이빗 듀얼 스택 서브넷을 설명하면서 `0.0.0.0/0` 의 대상을
`Igw-123456790123456` 으로 적었습니다. 같은 슬라이드의 다이어그램과 강사 노트는 NAT
게이트웨이라고 설명합니다. 표 쪽이 오기로 보이며, 이 문서 7.3 절에서는 NAT 게이트웨이로
적었습니다.

**같은 슬라이드 32 는 VPC 의 IPv6 CIDR 을 `2001:db8:1234:1a99::/56` 으로 적었습니다.**
두 가지가 어긋납니다. 첫째, 같은 덱의 슬라이드 18 과 서브넷 예시들은 같은 VPC 를
`2001:db8:1234:1a00::/56` 으로 씁니다. 둘째, `/56` 에서는 네 번째 그룹의 뒤 8비트가
호스트 비트이므로 **프리픽스 표기에서는 `00` 이어야** 합니다. `1a99` 는 호스트 비트에
값이 들어간 형태라 정렬된 `/56` 네트워크 주소가 아닙니다(2.2 절 참조).
이 문서 7.3 절에서는 `2001:db8:1234:1a00::/56` 으로 적었습니다.

### 11.2 동작·기본값이 변경된 항목

| 항목 | 교재 | 현재 |
|---|---|---|
| 퍼블릭 IPv4 요금 | 슬라이드 8 강사 노트에 "2024년 2월 1일부터 시간당 IP당 0.005 USD" 라는 단가가 적혀 있습니다 | 과금 사실은 맞습니다. 다만 단가는 바뀔 수 있어 문서가 요금 페이지로 안내하므로, 이 자료 본문에는 단가를 적지 않았습니다 |

### 11.3 비권장·지원 종료된 항목

### 11.5 검증하지 못한 항목

아래는 교재에 있으나 이번에 AWS 공식 문서로 확인하지 못한 항목입니다.
**교재 기술을 그대로 옮겼고, 단정하지 않았습니다.**

| 항목 | 교재 기술 | 상태 |
|---|---|---|
| IPAM 풀 깊이 | "기본적으로 풀은 최대 10개 깊이로 생성할 수 있습니다" | IPAM 문서에서 확인하지 못해 본문에 수치를 넣지 않았습니다 |
| IPAM 데이터 보관 기간 | "모니터링 데이터를 최대 3년까지 자동 보관" | 같은 이유로 본문에 수치를 넣지 않았습니다 |
| 다중 VPC ENI 연결 | 한 VPC 의 기본 ENI 로 인스턴스를 시작하고 다른 VPC 의 보조 ENI 를 연결 | 교재가 인용한 2023년 공지를 직접 확인하지 못했습니다 |
| 퍼블릭 IPv4 단가 | 시간당 IP당 0.005 USD | 요금 페이지를 직접 확인하지 않았습니다. 과금 사실만 본문에 적었습니다 |

교재 슬라이드 45 강사 노트에는 "모범 사례는 NAT 게이트웨이 리전입니다. 이 예는 NAT
게이트웨이 영역입니다"라는 문장이 있습니다. 번역이 어색해 의미가 불분명하지만,
8.3 절의 리전 NAT 게이트웨이와 영역 NAT 게이트웨이 구분을 가리키는 것으로 읽힙니다.
